# Four-surface contract: one record, four ways in, one person on it

Register row BR-218 (sources U-12, U-49, D-08). Written 2026-09-25 against `main` at 7cae45d6. Code facts below were read in this repository; facts about the PROJEXA repository (`FChecklist/projexa`) come from `surface_matrix.json` (commit e88b53e) and are marked as such.

## 1. The contract

The owner's four surfaces are the four keys in `surface_matrix.json` (`surfaces`). For each of the seven record types in that file, a person can create or change the same record through any of the four. The contract has five rules. A surface that breaks one of them does not count as proven.

1. **One record id.** All four surfaces write the same row in the same table (`record_type_tables` in `surface_matrix.json`). No surface keeps a copy, a draft table or a table of its own. Exceptions converge on the underlying flagged record (PMD-19). The first record type proven end to end is the BOQ line item, `compliance.construction_boq_line_items` (PMD-20, BR-402).
2. **One write function per record type.** A surface reaches the record's own service function, either through the shared pipeline (`runSubmission`, `runDirectTask`, `proposeSubmission`, `confirmSubmission` in `src/lib/pipeline/run-submission.ts`, then the executors in `src/lib/pipeline/executor.ts`) or through the record's own route. It never has a private write. Examples: `createProgressEntry` in `src/lib/services/construction-progress-service.ts` for daily work progress; `createBoq` and `createBoqRevision` in `src/lib/services/construction-boq-service.ts` for BOQ.
3. **The actor is a person.** The actor column of the record and `compliance.audit_logs.user_id` hold the `compliance.users.id` of an active user of that organisation. They never hold an `api_keys.id`, a link id or a service name. When an API key carries the call, the key is recorded next to the person, never instead of the person: `logActivity` in `src/lib/audit.ts` takes `dbUser`, `apiKey` and `actingViaApiKey: true` and stores `api_key_id` and `user_id` in one row (BR-214). A key-carried write with no acting person is refused with HTTP 400 (BR-215).
4. **The surface is recorded.** Each audit row for the write carries the surface key in the `compliance.audit_logs.surface` column (BR-415). One record written from all four surfaces has four audit rows with four distinct surface values (BR-417), each naming a real user (BR-418).
5. **The AI does not write on its own authority.** On s1 and s4 nothing is written until the person confirms a proposal (PMD-05 for email; the approve action for s1). On s2 the person presses Save. On s3 the calling AI writes directly only the level-1 functions the link allows; everything else is staged as a proposal for the person to confirm, and only that person can confirm it (BR-497). The gate that decides what the link may do compares the acting person, not the organisation key (BR-219).

## 3. How one record proves the contract

A cell of `surface_matrix.json` (one record type on one surface) is proven when its `record_id` is set and the audit rows for that id show the surface and a real person. The convergence command for a record type checks that its four cells carry one distinct `record_id`. For BOQ the runners are `scripts/verify/boq-surface-cells.sh` (BR-416), `boq-audit-surfaces.sh` (BR-417, four distinct surfaces) and `boq-audit-real-users.sh` (BR-418, each `user_id` exists in `compliance.users` and no `actor_role` is `api_key`). Phase 5 repeats this for the other six record types (BR-520, BR-521, BR-522).

## 4. What is true today, and what is not yet

- The identity helpers exist: `resolveActingUser`, `resolveWriteActorId`, `ACTING_USER_HEADER` and `ACTING_USER_EMAIL_HEADER` in `src/lib/supabase/auth-guard.ts`, and the key-plus-person variant of `logActivity` in `src/lib/audit.ts`.
- `compliance.audit_logs` has no `surface` column (BR-415), and `details` is TEXT. No writer stamps a surface, so no cell can be proven yet.
- `resolveWriteActorId` still falls back to the key's own id when a call carries neither acting header (its last branch returns `ctx.apiKey.id`). BR-215 replaces that fallback with a 400.
- Read in the code, not measured live: `POST /api/v1/projexa/tasks` builds `actorUserId` from the body field `actorEmail` only (`resolveActorUserId`), not from the acting headers, and passes the caller's key id as `userId`. The `record_work_progress` executor (`executeRecordWorkProgress` in `src/lib/pipeline/executor.ts`) writes `task.userId`, not `task.actorUserId`, into `recorded_by_id` through `createProgressEntry`. For a PROJEXA call that value is the key id. No register row names this column. BR-418 checks audit rows, not the record's own actor column.
- `surface_matrix.json` still carries the cell `verify_command` written before the key-plus-person audit row: it reads the surface from `details` as JSON (BR-415 and BR-417 use the `surface` column) and requires `api_key_id is null`. A correct s1, s2 or s4 write goes through PROJEXA's organisation key and now has both `api_key_id` and `user_id` set, so that clause would reject it. Rule 3 above is the intended reading: the row names the person, and the key may also be present. The cell commands need updating when BR-415 lands; this file does not change them.

## 5. What this document does not do

It does not build any of the routes, columns or scripts it names, does not prove any cell, and does not decide the open owner questions (OQ-11 email authority, OQ-19 the canonical link, OQ-20 the exception record). It fixes what "the same record, attributed to the person" means so that each proving row has one definition to test against.
