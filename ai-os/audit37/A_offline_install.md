## Point-by-point

### 1-3. Vercel used least / functions moved to Supabase - PARTIAL (BUILT-UNTESTED against real traffic)
Moved off Vercel (evidence):
- Sync read/write path is Supabase Edge, "No Vercel in the path": `supabase/functions/projexa-sync/README.md` L2-3; routes manifest/pull/changes/ids/heads/push/attest/release/install/prepare/jobs (`handler.ts` `routeOf` L188). Other Edge fns: ai-work-link, ai-work-link-exec, projexa-read, projexa-timer, projexa-scheduler-bridge, projexa-document-extract.
- Shell reads the IndexedDB replica; the service worker serves `/local` and static assets cache-first, never touching `/api/**` (`src/lib/local-first/release/sw-core.ts` header L8-27; `src/app/sw.js/route.ts`).
- vercel.json `ignoreCommand` skips non-main and docs-only builds; backend vercel.json `ignoreCommand: exit 0`.
Still on Vercel (the real gaps):
- 310 PROJEXA `src/app/api/**/route.ts` routes remain, each proxying to the backend on Vercel (`src/lib/veridian-client.ts:50` default `https://veridian-compliance-ai.vercel.app/api/v1/projexa`). Anything not in the shell uses them.
- Even shell screens call Vercel for: BOQ line edits (`shell/pending-edits.ts:100` -> `/api/scope/line-items/*`), analysis/exceptions/dashboard-project snapshots (`shell/modules/analysis-adapter.ts:43,66`, `dashboard-adapter.ts:72`), document file bodies (`documents-file-cache.ts:199-201`), prepare-report beacon (`src/app/api/local-first/prepare-report/route.ts`).
- Release bundle itself is served from Vercel static (`/_release/px-*.tar.gz`, `scripts/make-release.mjs`; Edge fn fetches `RELEASE_MANIFEST_URL` from projexa-ai.com, `handler.ts` L97). Static/CDN, cheap, but not zero. Login/signup pages and middleware are Vercel.
- Backend crons (200+ in backend vercel.json) are Vercel functions, outside PROJEXA scope but part of "Vercel used least" for the whole product.
- Cost model exists: `src/lib/local-first/cost/*` (harness, budget; workday 209 req/laptop, memory notes ~108 laptops fit 500K free invocations). Never measured with real users.
Tests: cost-budget/replica-cost/scheduler-cost/replica-breaker unit tests; `conformance/wire.integration.test.ts` and `parity.test.ts` (real client x real Edge handler on PGlite; need `CT_ROOT`, CI job "Local-first wire conformance (non-required)").
Suggested proof: a counted-request e2e/RUM check: log in as a seeded real user on a built app, work through one scripted day, and assert Vercel-origin requests (everything except `/_next/static`, `/_release`, `/local`, Supabase hosts) <= N; read Vercel usage dashboard for 48h with 3 real users. Add a CI grep guard that lists every `/api/` fetch reachable from `/local` shell code and fails on new ones.

### 6. Whole app (files, DB, functions) downloaded via browser in background - PARTIAL
- App code: BUILT-UNTESTED-in-real-world. `scripts/make-release.mjs` bundles `.next/static/**`, `public/**` and the prerendered `/local` shell into one deterministic gzip tar with per-file sha256 manifest; `installer.ts`/`verified-install.ts`/`verified-install-browser.ts` verify digests and install into Cache Storage `px-release-<ver>`. Tests: bundle/canonical/installer/sw-core unit tests; `e2e/lf-lifecycle-install.spec.ts`, `lf-lifecycle-release.spec.ts` (sha mismatch refused, cut download, N+1 update).
- Pages: only the `/local` static shell is cached; each screen is a client component in `shell/route-table.ts` (~85 patterns across 9 cluster files). Modules without an entry are NOT on the laptop.
- DB: IndexedDB replica of 28 project kinds + org kinds (0678-0691), signed rows, change feed (`/heads`, `/changes`). Per-role redaction; money/approval figures withheld for some roles. Not "the whole DB": payroll, recruitment, grc, kpis, CRM leads, leave, loans, journal/budget/PO/quotation LINE items, proposals/copilot are not syncable (memory note + route-table comments L44-46).
- Files: NOT downloaded in background BY DESIGN (`documents-file-cache.ts` header L3-12): only user-pinned (500 MB cap) or recently opened (150 MB cap) files, max 60 MB each. This contradicts the literal wording of point 6.
- Functions: server functions are not downloaded; they cannot be. Compute is limited to leased display-only jobs (`jobs/*`, 0682). Writes that need server logic are queued and executed server-side by `ai-work-link-exec` after reconnect.
- "In background": the install is a blocking mandatory prepare screen (3-min ceiling, `prepare-workspace.ts:12`), then quiet re-sync. Updates are background (`boot.ts`).
Suggested proof: real-Chromium, real build, real projexa-sync (Supabase branch or staging org): sign in, wait for 100%, then block ALL network except localhost and assert every route in `SHELL_ROUTES` renders non-empty with seeded data (generate the list from route-table, so new routes are covered automatically), and a negative table asserting each non-shell route shows the calm "not on this laptop" page.

### 15. First login downloads everything; laptop = daughter server - PARTIAL
- First-login flow: BUILT-VERIFIED in stubbed e2e. `src/components/WorkspacePrepare.tsx` steps worker 15 / app 45 / database 10 / projects 30 (L101-181), mandatory and quiet (L204+), retries every 15 s, auto-opens at 100%. `LocalFirstDefault.tsx` turns on `px-local-first` for signed-in browsers (a real bug found by e2e, fixed). Failure reporting to `platform.projexa_prepare_*` + `.github/workflows/projexa-prepare-health.yml` (every 10 min). Tests: `WorkspacePrepare*.test.tsx`, `prepare-workspace`, `prepare-report.test.ts`, `e2e/lf-lifecycle-install.spec.ts` (case 1 new login, case 2 new machine), `e2e/lf-lifecycle-monitor.spec.ts`, `e2e/lf-dubai-user.spec.ts` (Asia/Dubai, slow link).
- Gaps: (a) `projects` step lets a partial copy through when only project-level issues occur (L177), so "everything" is not guaranteed; (b) the "app" step needs `release/register` on Supabase to succeed, so first install fails (screen stays up, retries) whenever the sync service is down; (c) per memory 2026-10-03, the release registry had 0 installs: no real laptop has ever registered a release or completed a prepare against production; (d) rate cap 120 req/min vs 1+P requests per first sync (pacer exists, `rate-pacer.ts`, circuit breaker status unverified); (e) Safari/iOS 7-day eviction, mobile, low-storage untested.
- Daughter server: laptop<->laptop sync is code-complete (`peer/*`: WebRTC, ES256 attest, holder binding, sig3 verification, auto-sync; `playwright.peer.config.ts`, `e2e/lf-peer-auto|signed|versions.spec.ts`, `peer-sync.spec.ts`) but only proven between two Chromium contexts on one machine with a fake signaller (`__fixtures__/fake-signalling.ts`, `memory-rtc.ts`). Signalling uses Supabase Realtime, BroadcastChannel, ntfy (`peer/signalling.ts` L6-8); STUN is Google/Cloudflare (`peer/transport.ts:21-22`) - no TURN, so symmetric NAT/corporate networks will fail. A laptop never serves HTTP to another; it only exchanges signed rows. Org-wide "all laptops equal" convergence under conflicts is unit-tested (`outbox-merge`, versions) not field-tested. Deletes: tombstones via change feed (D3) but memory says "deletes not synced" in the earlier state; re-verify.
Suggested proof: two real machines (or two browsers with real internet) on different networks, real accounts in the same org: A creates/edits offline, B receives via peer with the Supabase relay blocked at the firewall; assert B's IndexedDB row version and signature. Add a first-login test against a staging Supabase project with a seeded org of realistic size (500 rows x 28 kinds) measuring time-to-100% and request count.

### 26. Works with user's internet up but git/Vercel/Supabase down - PARTIAL (BUILT-VERIFIED for Vercel/sync down; Supabase-Auth-down partly)
- Evidence: R2 test (`offline-local-first.spec.ts:290`): sync service and `/api` refused, edit waits and syncs later. SW falls back on 5xx/network error, and in local-first mode never asks the server. Release is pinned in Cache Storage so a Vercel outage or pause (`projexa` deployments) leaves installed laptops running. Git is irrelevant at runtime. R9 test kills the auth endpoint and the person stays in.
- Gaps: (a) a Vercel response that is not 5xx (e.g. 404 DEPLOYMENT_NOT_FOUND, 402/403 paused project page) is not covered by the "5xx" rule if local-first mode is OFF; verify with local-first on only; (b) a person who has NOT yet installed cannot get in at all (login page is Vercel + Supabase Auth); (c) peer signalling needs Supabase Realtime, with ntfy as fallback (third party), so laptop<->laptop sync with Supabase down depends on ntfy (`peer/signalling.ts`) and has no real-network test; (d) update/release check, install records, prepare reports are queued but all need Supabase; (e) sync requires the PROJEXA Auth JWT; once it expires with Supabase Auth down, pushes fail until it returns (queue is kept); (f) sign-out with Supabase down - `signOutEverywhere` is wired (memory) but confirm it clears local state without network.
Suggested proof: a "chaos" Playwright config that uses real hosts but a proxy (or `page.route` aborting only `*.supabase.co`, `*.vercel.app`, `projexa-ai.com` after install) while leaving other internet reachable; run the same walk as point 25 plus a write; then restore and assert the write lands once (no duplicates) and the peer receives it.
