# UMR / UTM Naming-Collision Discovery — Universal Knowledge and Execution Architecture

**UMR:** parented to `UMR-20260802-165606-4413` (OCID-020). Discovery/analysis only, per the SPEC's own
explicit instruction and the standing OCID-020 discovery-only lock (`SEC-07`, `ai-os/CONSTITUTION.yaml`).
**No schema change, no code change, no database change, no new architecture in this document or its
production.**

Zero-duplication check performed first: full read of `ai-os/boss/ACTIVE-CLAIMS.yaml` and a targeted scan
of `ai-os/OS.yaml`'s index for an existing "UMR vs UTM naming collision" artifact — none found. The
closest prior work, `ai-os/VERIDIAN_GLOBAL_KNOWLEDGE_DISCOVERY_AND_REUSE_RUNTIME_2026-08-03.md` (OCID-027),
is a discovery/reuse *search-order* operating model (which registry to query in what order before
building anything new) — it does not analyze this specific naming collision, so this document is a real
addition, not a duplicate.

## 0. What the Owner asked for, verbatim intent

A single **Universal Metadata Registry (UMR)** holding reusable knowledge as UMR records, a
**Universal Task Metadata** model (**UTM**) describing every executable task across identity,
governance, execution, business, knowledge-reference, and evidence contexts, and an **End User Identity
(EUID)** combining brand id + organization id + end user, synchronized across server, browser, and PWA.

This document compares that proposal against what is **actually live today**, read directly from the two
named scripts and the real SQLite schema they operate on (Python `sqlite3` introspection against
`/opt/veridian/ai-os/memory/superboss-register.sqlite`, not just source-reading) — plus one adjacent
question (EUID) the SPEC's own naming-collision framing made it necessary to check.

## 3. The naming collision the SPEC asked to confirm: `utm_*` columns

Confirmed, and **wider than the SPEC's own framing** (which named 4 tables). Live introspection found
**8** tables in `superboss-register.sqlite` carrying one or more `utm_*` columns:

| table | utm columns present | rows |
|---|---|---|
| `instructions` | all 5 | 3,047 |
| `work_items` | all 5 | 1,285 |
| `actions` | all 5 | 18,864 |
| `system_index` | `utm_term` only | 135 |
| `knowledge_engine` | all 5 | 377 |
| `capability_registry` | all 5 | 11 |
| `umr_tasks` | all 5 (added 2026-07-29, Phase 6) | 1,081 |
| `task_claims` | `utm_source` only | 43 |

Per `superboss-register.py`'s own module docstring, these are **literal UTM (marketing) parameter
names**, chosen deliberately because that's the vocabulary already in use: `utm_source` (who:
`owner|end_user|org|ai_agent|software`), `utm_medium` (channel:
`ssh_session|claude_code_cli|chat_ui|api|cron`), `utm_campaign` (initiative/project slug), `utm_content`
(short structured label), `utm_term` (comma-separated search keywords). This is a **search/audit tagging
convention**, not a task-metadata object model — confirmed by reading every `_derive_*_utm_fields()`
function in the source (e.g. `_derive_umr_utm_fields()`, line 2787): each derives a short classification
string, never an object with governance/execution/business/knowledge-reference/evidence sub-structure.

**This is a real, live, three-letter-abbreviation collision** between the Owner's proposed "Universal
Task Metadata" (UTM) object model and this pre-existing, CI-adjacent, actively-growing (43,673 combined
rows across 8 tables as of this pass, added to as recently as 2026-07-29) marketing-style tagging
convention using the identical acronym for a semantically unrelated purpose.

## 4. A deeper collision the SPEC did not anticipate: "UMR" already has two other live meanings

While confirming §2, this discovery surfaced that **"UMR" is already an overloaded abbreviation in this
codebase before the Owner's new spec introduces a third meaning**:

### 4a. "UMR" already means "Universal Metadata Registry" — verbatim the same name

`ai-os/OS.yaml` (line 109, `health_and_compliance` section) literally reads:

> `ai-os/registry/asset-registry-coverage.yaml` — "**UMR (Universal Metadata Registry)** coverage
> manifest — every DB table must be listed registered or exempted, enforced by
> `scripts/check-asset-registry-coverage.mjs` on every PR."

`scripts/check-asset-registry-coverage.mjs`'s own header (line 4) independently confirms the same name:
`// Universal Metadata Registry, same enforcement class as...`. This is a real, live, CI-enforced system
(Priority 4, since 2026-07-12): every table in `src/lib/db/schema.ts` must appear in
`asset-registry-coverage.yaml` as either `registered` (a `compliance.asset_registration_config` row +
`auto_register_asset` Postgres trigger attached — real row-level auto-registration) or `exempted` (a
specific reason). This is a **DB-table/row asset-registration system**, not a reusable-knowledge store.

**The Owner's proposed name for the new concept — "Universal Metadata Registry" — is not just an
abbreviation collision, it is an exact, verbatim full-name collision with a system that already exists,
is already CI-enforced, and already answers a related-but-different question** ("is every DB table
accounted for in the asset registry", not "what reusable knowledge exists").

### 4b. "UMR" is also the literal ID prefix for `resource_governor.py`'s task-dispatch queue

As shown in §2: every `UMR-YYYYMMDD-HHMMSS-hex` ID cited as a "PM decision" / "master directive" /
parent reference throughout `ACTIVE-CLAIMS.yaml` and every OCID doc in this project (including this
task's own governing SPEC, `UMR-20260802-165606-4413`) is a real row in `umr_tasks`, whose own code
comment names it **"Universal Task Metadata Record."** This is, in substance, far closer to what the
Owner is now calling **"UTM" (Universal Task Metadata)** than to a knowledge registry — the existing
system already built a per-task metadata record under the *UMR* label, while the Owner's new spec wants
to build a per-task metadata model under the *UTM* label. The two proposed names and the two pre-existing
systems are effectively **crossed**: the live "UMR" already behaves like the proposed "UTM," and no live
system currently occupies the exact "reusable knowledge registry" role the Owner wants "UMR" to mean.

### 4c. Closest existing functional analog to "reusable knowledge as UMR records": `knowledge_engine`

Not a naming collision, but material to any future PM decision on what to build vs. reuse:
`knowledge_engine` (377 rows, confirmed §3) already stores `artifact_id`, `artifact_path`,
`content_hash`, `artifact_type`, `secondary_path`, `exists_on_disk`, `purpose`, `tags`,
`entity_relationships` (JSON), `last_verified_ts`, `verification_status` — i.e. a searchable,
drift-checked registry of real artifacts and their relationships. This is the closest existing thing to
"reusable knowledge records" in the live system today, and it carries neither the "UMR" nor "UTM" name.
Any future PM decision on the Owner's proposed registry should evaluate extending this table before
proposing a new one, per the existing `ai-os/MASTER_INDEX.yaml` search-before-build protocol.

## 5. EUID (End User Identity: brand id + organization id + end user)

No collision found — this concept is **genuinely new**. Confirmed by direct repo research
(`src/lib/db/schema.ts`, PWA/service-worker code, auth guard):

- The literal string `EUID`/`euid` does not appear anywhere in source, docs, or planning files (the only
  `git grep -i euid` hit is inside a compiled binary, `bin/officecli-linux-x64`, almost certainly the
  unrelated POSIX `geteuid()` symbol).
- No table or column combination joins `brandId` + `organizationId` + `userId` into one composite
  identity. The closest composite-identity table is `stage0Sources`, keyed on `(userId, orgId)` only —
  explicitly documented in its own schema comment as "the ONE place... a single auth identity can have
  more than one organisational relationship" — with no brand dimension.
- There is no `brands` table. Multi-brand is modeled two separate, uncombined ways: `productBranches`
  (platform-level product catalog — `grc`/`pms`/`erp` branch keys, e.g. "PROJEXA") linked via
  `organisations.primaryProductBranchId`, and per-org white-label columns
  (`organisations.brandPrimaryColor`/`brandAccentColor`/`customDomain`/etc.) read by
  `org-branding-service.ts`. Neither is a per-end-user identity concept.
- No server/browser/PWA identity-sync mechanism exists to extend: `src/app/manifest.ts` is a plain
  Next.js PWA manifest with no identity payload; no service worker exists anywhere in `src/`
  (`next-pwa`/`workbox` absent); `src/lib/browser-execution/sync-engine.ts` is an offline
  entity-CRUD-conflict-resolution queue with no brand/org/user concept in it; auth/session identity is
  handled server-side only via `src/lib/supabase/auth-guard.ts`.

**Recommendation for a future PM decision**: EUID can proceed as new work without a naming or schema
collision to resolve first — it is the one piece of the Owner's spec this discovery did not need to gate.

## 7. What this document recommends, and does not decide

Per the SPEC's own explicit instruction, **this document makes no naming decision** — that is reserved
for the next PM decision, informed by the findings above. It recommends that PM decision consider, at
minimum:

1. Do **not** rename or restructure any existing `utm_source`/`utm_medium`/`utm_campaign`/`utm_content`/
   `utm_term` column anywhere (8 tables, 43,673+ live rows) — a live, actively-queried tagging/search
   convention, not a placeholder.
2. Do **not** reuse the bare "UMR" abbreviation for the Owner's new "reusable knowledge registry" concept
   without first resolving its collision with (a) `asset-registry-coverage.yaml`'s existing, CI-enforced,
   verbatim-identical "Universal Metadata Registry" name, and (b) `resource_governor.py`'s `umr_tasks`
   queue, whose IDs are already cited pervasively as "UMR-..." throughout this project's own governance
   trail, including this SPEC's own parent citation.
3. Consider whether the Owner's "Universal Task Metadata" (UTM) concept is better served by **extending**
   `umr_tasks` (§4b — already structurally closer to a per-task metadata record than any other live
   table) under a new name than by building a new object model that collides with the marketing-UTM
   convention.
4. Consider whether the Owner's "reusable knowledge as UMR records" concept is better served by
   **extending** `knowledge_engine` (§4c) than by building a new table.
5. EUID (§5) has no naming or schema collision and can be scoped independently of the UMR/UTM naming
   question.

No new table, model, schema, or parallel architecture was created by this document. No existing column
was renamed or altered.
