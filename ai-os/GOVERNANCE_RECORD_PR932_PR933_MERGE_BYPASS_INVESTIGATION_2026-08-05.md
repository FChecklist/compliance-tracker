## The real mechanism (why GitHub allowed the merge)

Three independently-verified facts combine to explain this without needing to guess:

1. **`FChecklist` holds real repository-owner/`admin` permission** on `FChecklist/compliance-tracker` (confirmed via `gh api repos/.../collaborators/FChecklist/permission` → `"permission":"admin"`, `"role_name":"admin"`). `FChecklist/compliance-tracker` is owned by a personal user account, not an organization — there is no separate "org owner" tier above this.
2. **Branch protection's `enforce_admins` ("Include administrators") was almost certainly OFF at the moment of both merges.** This is not this task's own inference — it is what a real, already-merged governance record in this same repository already states as the reason it made a corrective change: `ai-os/GOVERNANCE_RECORD_TEMPORARY_REVIEW_COUNT_EXCEPTION_2026-08-05.md` records that `UMR-20260805-034917-33a9` (timestamped ~03:49:17Z, roughly 25–29 minutes *after* both merges) **added** `required_approving_review_count: 1` **and** `enforce_admins: true` to `main`'s branch protection "as real corrective action for a real finding: PRs #932/#933 had merged with a failing required check and zero reviews." Live re-confirmation today: `enforce_admins.enabled` is currently `true` and `required_status_checks.contexts` currently includes `Metadata Index Coverage Check` — both consistent with that same corrective change still being in effect, not with either setting having been in effect before it.
   - **Honest limitation:** this repository is a personal-account repo, so GitHub's organization audit-log API (which would show a timestamped history of protection-setting changes) returns `404` here — there is no independent, GitHub-native way to directly confirm the pre-merge value of `enforce_admins` beyond the already-merged governance record's own contemporaneous account. This record relies on that account plus the mechanical consequence it implies; it does not fabricate a value GitHub itself will not confirm.
3. **The automation that actually fired the merge (`ai-os/scripts/supervisor-entrypoint.sh`) calls a plain `gh pr merge "$PR_URL" --merge --delete-branch` — no `--admin` flag.** Its only pre-merge readiness gate polls `gh pr view --json mergeStateStatus` and proceeds once that value is anything other than `BLOCKED` or `BEHIND` (`ai-os/scripts/supervisor-entrypoint.sh:176-181`). GitHub computes `mergeStateStatus` relative to the *specific actor* attempting the merge: for an actor who can bypass a failing required check (an admin, with `enforce_admins` off), GitHub reports `UNSTABLE` — "mergeable, with non-passing required checks the current actor is allowed to bypass" — not `BLOCKED`. The polling loop treats `UNSTABLE` as "not blocked" and proceeds. **No one issued an explicit override command; ordinary automation, run by an account that happened to hold admin rights on a branch whose `enforce_admins` flag was off, was sufficient on its own.**

Put together: this was a real, structural gap — an admin-permission account merging through standard, unprivileged-looking tooling, on a branch protection configuration that (at that specific moment) did not actually enforce either the failing check or a review requirement against that account. It required no one to knowingly bypass anything; the merge command succeeded exactly as GitHub is documented to behave under that configuration.
