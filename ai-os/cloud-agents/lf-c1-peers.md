# Package lf-c1-peers (laptop app, repo projexa)

Branch `claude/lf-c1-peers` from `origin/feat/lf-client-core` if it exists, else `origin/feat/local-first-complete` (then code against interfaces you define and keep them injectable).

## Goal (requirements G3, R2, R3)
Two or more laptops of one organisation sync DIRECTLY with each other, automatically, with no server in the data path, and keep doing so while OUR server (Supabase) is down.
Read CONTRACT.md section 4 (peers) and the backend's `/attest` (`supabase/functions/projexa-sync/handler.ts` `attest`, `sign.ts`, compliance-tracker `origin/feat/lf-sync-backend`): a 24-hour ES256-signed attestation `{sub, org, projects, view, iat, exp}` + the public keys + an organisation channel name. Every pulled row is signed ES256 over `px2|org|project|kind|id|version|updated_at|sha256hex(canonicalJSON(data))`, and a record carries `version`, `sig`, `kid`.

## Build under `src/lib/local-first/peer/`
1. `verify.ts`: WebCrypto ES256 verification of attestation tokens and of row signatures with the SAME canonical JSON (assert the shared test vector: see `TEST_VECTOR` in `supabase/functions/projexa-sync/sign.ts` and the same constants in CONTRACT.md); key lookup by `kid` from the cached public keys (cached in the local database so verification works with our server down).
2. A SIGNALLING abstraction with providers: (a) Supabase Realtime broadcast + presence on the channel `px:<channel>` using PROJEXA's own Supabase client (`src/lib/supabase/client.ts`); (b) `BroadcastChannel` for tabs/windows of one browser; (c) a FREE PUBLIC fallback used when (a) fails (our server down): ntfy.sh topics derived from the channel (SSE subscribe + HTTP publish, no account), signalling messages only (SDP/ICE, never data), rate-limited and size-capped. Providers are tried in parallel and the first that connects wins.
3. Transport: WebRTC `RTCPeerConnection` + `RTCDataChannel` with public STUN (`stun:stun.l.google.com:19302`, plus a second public STUN) and NO TURN (free only); an in-memory transport pair for tests.
4. The protocol over the channel: `hello{token}` (reject unless the token verifies, is unexpired, same org AND same view class as ours) -> `have{per project: kind -> max server version/updated_at summary}` -> `want` -> `items{signed rows}` in size-capped batches. The receiver verifies every row signature, only accepts rows for projects in BOTH attestations, only rows whose version is higher than its local `serverVersion`, never rows for a record it holds as dirty, never tombstones or versions of its own. The sender never sends a dirty row or a row without a valid server signature.
5. The auto-sync scheduler (cost-aware, R3/R14): runs with no user action on app open, on coming online, on a long timer (default 5 minutes; backs off to 30 minutes when idle/hidden; none while the tab is hidden for long unless peers are connected), and on peer discovery; server sync first when reachable (cheap: a `/changes` head check before any pull), peer sync in parallel; NEVER a tight loop; one flight at a time (Web Locks); everything injectable (clock, transport, signalling, storage).
6. A small hook/UI marker "Synced with 2 laptops" (calm, no dialogs).

## Tests
Unit tests with the in-memory transport pair and fake signalling: tampered row refused; wrong org refused; wrong view class refused; expired attestation refused; a row for a project not in both tokens refused; older version ignored; a dirty row never overwritten and never sent; two simulated laptops converge from different starting data; the scheduler's back-off and no-storm behaviour with a fake clock; provider fallback order (Supabase down -> the ntfy path is chosen); verification works with the server unreachable (cached keys). Plus a Playwright spec `e2e/peer-sync.spec.ts` for CI (two browser contexts, same origin, loopback WebRTC): write it carefully and mark it as not run by you.
PLANT bugs: signature check skipped, org check skipped, view-class check skipped, dirty rows sent, scheduler ignoring a hidden tab; each must be caught.
