## Goal (requirements R4 and G5)
"A user sees their own organisation's data as per role." The sync carries 28 PROJECT-scoped kinds so far (see `drizzle/0683_projexa_sync_more_kinds.sql`). It must also carry the ORGANISATION-LEVEL master data that the visible PROJEXA screens read, so a laptop can work offline:
vendors (`erp_suppliers`), customers (`erp_customers`), companies (`erp_companies`), BOQ categories (`construction_boq_categories`), currencies and exchange rates (`erp_currencies` and the rates table), departments (HR departments), organisation people (`compliance.users`: id, name, role, is_active; email masked for everyone but the person themself exactly as the AI link masks it: `public.ai_work_link__mask_email`), and the cost-visibility configuration (`compliance.cost_visibility_config`) so the laptop can show or hide cost fields consistently.
Find the real tables and columns in `src/lib/db/schema.ts` and the existing services (`src/lib/services/*`) and see how the PROJEXA screens use them (the projexa repo is cloned too: grep `src` for `/api/vendors`, `/api/companies`, `/api/customers`, `/api/scope/categories`, `/api/currencies`, `/api/hr/departments`, `/api/org-users`). Put what you found in a short table in your report.

## Design constraints
1. These kinds are NOT project-scoped: the manifest lists them with `project_scoped:false`; `POST /pull` for them takes no `project_id`; `/changes` and `/ids` need an organisation-level form (for example a sentinel project id `__org__` in `platform.projexa_change_log` and `platform.projexa_record_head`, or a separate organisation feed: choose, document, and make versions and tombstones work for them exactly as for project kinds). The trigger function `platform.projexa_track_change` (0679/0683) is the place to extend; the single project kind list is `public.projexa_sync__kinds()`: keep project kinds and org kinds separate (e.g. a second function `projexa_sync__org_kinds()`).
2. AUTHORITY: the person is resolved by `public.projexa_read_resolve_user` as for every other kind; the organisation scope is mandatory in every query. Add a ROLE GATE with a minimum role rank per kind (member and above for vendors, customers, companies, categories, currencies, departments, people; a viewer or client_viewer must NOT receive vendor, customer or company master data: check role names and ranks in `public.ai_work_link__role_rank`) and an explicit COLUMN ALLOW-LIST per kind (never `select *`: exclude bank accounts, tax ids, secrets, passwords, tokens, internal notes, anything personal beyond name and work contact). Money-like columns follow the existing redaction (`ai_work_link__hidden_cols`, `cost_visibility_config`) where it applies.
3. Pull is keyset on (updated_at or created_at, id) like 0677 with the same opaque cursor; every item is signed with the same ES256 signature by the handler (for org kinds the project field of the signed message is the sentinel).
4. Additive only.
5. The laptop client does not consume these yet (another engineer extends the replica later): document the wire format of the org kinds in `supabase/functions/projexa-sync/README.md`.
6. Extend the kind handling in `supabase/functions/projexa-sync/handler.ts` so org kinds are accepted on `/pull`, `/ids` and `/changes`, with the same one-404 rule for anything the person may not read.
