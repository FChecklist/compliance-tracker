## [BLOCKER] requirements-coverage:F1  supabase/functions/projexa-sync/handler.ts  (127 (corsHeaders); projexa client sync-client.ts:356; test projexa-sync-read.pglite.test.ts:358)

**Issue:** The CORS preflight answer allows only the request headers `authorization, content-type`. The laptop sends a custom `X-Px-Client` header on every call, so a real browser refuses every call to the function before it is sent.


**Scenario:** projexa-ai.com (or localhost:3100) calls GET https://pcrjmlpuqsbocqfwoxod.supabase.co/functions/v1/projexa-sync/manifest with Authorization + X-Px-Client. The browser first sends OPTIONS with Access-Control-Request-Headers: authorization,x-px-client. The function (handler.ts:160) answers 204 with Access-Control-Allow-Headers: authorization, content-type. x-px-client is not CORS-safelisted and is not listed, so the preflight fails: manifest, pull, changes, ids, push, attest, release and install are all blocked in Chrome, Edge, Firefox, Safari. Every requirement served over HTTP (G2, G3, V1, R2, R3, R12) is dead from a browser, and the node-based tests cannot see it.


**Evidence:** handler.ts:127 `"Access-Control-Allow-Headers": "authorization, content-type"`; handler.ts:483 reads `x-px-client`; client sync-client.ts:356 sets `"X-Px-Client"` with credentials omitted on a cross-origin base URL (SYNC_BASE_URL on supabase.co); the only CORS assertion is `expect(...allow-headers).toContain("authorization")` (projexa-sync-read.pglite.test.ts:358). The client also reads `Retry-After` on 429 (sync-client.ts) but the function sets no Access-Control-Expose-Headers, so a browser hides it.


**Suggested fix:** Set Access-Control-Allow-Headers to `authorization, content-type, x-px-client` and add `Access-Control-Expose-Headers: Retry-After`. Extend the CORS test to assert the exact preflight a browser sends (Request-Headers authorization,content-type,x-px-client) is allowed, and that an unknown header is not.


**Verified fix:** handler.ts:127: Access-Control-Allow-Headers 'authorization, content-type, x-px-client'; add 'Access-Control-Expose-Headers': 'Retry-After'; set Access-Control-Max-Age to 7200 (see F3). Replace the CORS test with a real preflight: OPTIONS with origin http://localhost:3100 and Access-Control-Request-Headers 'authorization,content-type,x-px-client'; assert every requested header name is present in the allow list (split on comma, trim, lowercase), allow-credentials is absent, and a disallowed origin gets no allow-origin. Do this before deploying the function.

## [MAJOR] edge-handler:F-02  supabase/functions/projexa-sync/handler.ts  (574-693 (push loop), 79-94 (RateLimiter); drizzle/0681_projexa_sync_push.sql 84-105, 134-164)

**Issue:** The push path multiplies one request into up to 50 begin RPCs + 50 exec invocations + 50 finish RPCs, and the SQL caps meant to bound that are not applied where it matters: the 600-ops/hour cap runs only when `NOT v_had` (a re-run of a failed or needs_server op is never counted, line 158) and refused ops (BAD_OP, FUNCTION_NOT_ALLOWED, ROLE_TOO_LOW, PROJECT_NOT_READABLE) never write a ledger row, so they are never counted. Shape validation in the SQL happens only after projexa_read_resolve_user and projexa_sync__ctx have already run (lines 88-105), and the edge does no pre-validation of op shape.


**Scenario:** A linked person with any role that may run at least one registered write sends POST /push with 50 ops that are guaranteed to fail the same way each time (for example valid function_id but params that make exec answer 400, see F-03, or a function with no executor -> needs_server) re-using the same op_ids. Each re-send re-enters begin (resolve user + ctx + ledger FOR UPDATE + upsert), calls the exec function (one Edge invocation each), and finishes (another UPDATE). Nothing in SQL counts these attempts; the only limit is 120 requests/min per isolate. 120 x 50 = 6000 ledger upserts, 6000 exec invocations and 12000 RPCs per minute per isolate, against the shared live database that DPDP customers use. Even pure garbage ops (`{}`), which never reach exec, cost one resolve+ctx RPC each (50 per request).


**Evidence:** 0681 line 158: `IF NOT v_had AND (SELECT count(*) ... ) >= 600`; lines 134-155 show failed/needs_server rows fall through to a re-run; lines 98-105 shape check comes after the user/ctx resolution; handler.ts line 609 calls projexa_sync_push_begin for every op with no cap other than ops.length <= 50 (line 581).


**Suggested fix:** Count attempts, not rows: add an attempts counter (or a separate counter table) incremented on every begin that reaches 'run', cap re-runs of one op (for example 3), and apply the hourly cap to every begin call including refusals. In the edge, reject malformed ops (op_id regex, function_id regex, params object, size) before any RPC, and add a per-person budget in SQL or a shared store rather than in isolate memory.


**Verified fix:** Count attempts, not rows: add an attempts counter or a small per-person counter table, incremented on every begin that is not a pure shape reject. Cap re-runs of one op (for example 3, then terminal) and apply the hourly cap to refusals too. In the edge, validate op_id, function_id, params-is-object and size before any RPC. Resolve person and ctx once per request instead of once per op, or short-circuit the rest of the batch after N consecutive refusals. Keep a per-person budget in SQL, not isolate memory.

## [MAJOR] edge-handler:F-03  supabase/functions/ai-work-link-exec/handler.ts  (80, 149-151 (exec byte cap); supabase/functions/projexa-sync/index.ts 74; drizzle/0681_projexa_sync_push.sql 101; handler.ts (projexa-sync) 580-583, 305)

**Issue:** The size limits of the three layers disagree and the disagreement produces a poison op that retries forever. SQL accepts an op when length(p_op::text) <= 65536 CHARACTERS; the edge accepts a 262144-char body; the exec function refuses a body above 72 KiB measured in BYTES (SYNC_BODY_MAX_BYTES = 73728, UTF-8). Any op with enough multi-byte text passes begin but is answered 400 BAD_REQUEST by exec. index.ts line 74 maps exec 400 to {kind:'unavailable'}, which the handler records as ledger status 'failed' with code SYNC_NOT_AVAILABLE (handler.ts lines 680-685), a code the handler documents as 'nothing was written and trying again later may work' (TRANSIENT_CODES).


**Scenario:** A site-diary or meeting-minutes edit written in Hindi (Devanagari, 3 bytes per character) with params.note of 25,000 characters. Probe result: op chars 25090 (SQL cap 65536, passes), exec body bytes 75174 (cap 73728); handleExec answered `400 {"ok":false,"code":"BAD_REQUEST"}`. Edge turns that into status 'failed' / SYNC_NOT_AVAILABLE, the laptop is told it may retry, and every retry repeats begin + exec + finish forever (and, per F-02, is not counted against any cap). The user's edit can never be saved, with no error that says why.


**Evidence:** Scratch probe output: `op chars (SQL length(p_op::text) cap 65536): 25090 | exec body bytes (cap 73728): 75174` then `exec answer for that op: 400 {"ok":false,"code":"BAD_REQUEST"}`.


**Suggested fix:** Make the layers agree and in bytes: have the SQL measure octet_length(p_op::text) <= a number the exec accepts (for example 60000), or raise SYNC_BODY_MAX_BYTES to 4 x 65536 plus envelope; in the edge map exec 400 to a terminal 'rejected' (code BAD_OP/TOO_LARGE) instead of 'unavailable', and check the byte length of the op before calling begin.


**Verified fix:** Measure bytes in SQL (octet_length(p_op::text) <= about 60000, or raise exec's SYNC_BODY_MAX_BYTES to cover 4 x 65536 plus envelope) and add the same byte check in the edge before begin. In index.ts map exec 400 to a terminal {kind:'failed', code:'BAD_OP'} (finish as 'rejected'), not 'unavailable'. Keep 401/404/503 as 'unavailable'. Add a test with a 3-byte-script op between 24.5K and 65K characters.

## [MAJOR] edge-handler:F-07  supabase/functions/projexa-sync/handler.ts  (574-693; supabase/functions/projexa-sync/index.ts 58-84)

**Issue:** push() has no overall deadline: it runs up to 50 ops strictly one after another, and each exec call may take up to EXEC_TIMEOUT_MS = 25 s, so the worst case is about 1250 s against a platform request limit of a couple of minutes. When the platform ends the request mid-batch, the op in flight is left 'running' and is only moved to 'uncertain' 10 minutes later (0681 lines 147-152), after which it is terminal: begin answers retry EXECUTION_UNCERTAIN for that op_id forever and nothing in 0678-0683 ever resolves an 'uncertain' op. The same terminal state is also reached when exec returns any non-OK status other than 400/401/404/503 (index.ts line 75), including statuses where nothing could have run (405, 413, 429).


**Scenario:** A laptop comes back online after a week with 300 queued edits and pushes in batches of 50; exec cold start plus a Postgres connect make each op take about 3 s, so a batch needs about 150 s and the gateway cuts the request. The op that was running becomes permanently EXECUTION_UNCERTAIN after 10 minutes, the laptop gets status 'failed' for it (indistinguishable by status from a retryable failure), and the user's edit is stuck until the client invents a new op_id (risking a duplicate if the write had in fact landed).


**Evidence:** handler.ts push loop awaits execRun inside `for (const raw of ops)` with no clock check; no deadline variable exists; index.ts line 75 `if (!res.ok) return { kind: "uncertain" }`; 0681 lines 144-146 return retry EXECUTION_UNCERTAIN unconditionally for status 'uncertain'.


**Suggested fix:** Give push a deadline (for example 90 s from `now`): once exceeded, answer the remaining ops with a distinct retryable code (RETRY_LATER) without calling begin, and return what was done. Return a distinct status (not 'failed') for EXECUTION_UNCERTAIN so clients cannot loop on it, and add a resolver (for example after 10 minutes look for the record or the submission note '[ai-link px-sync:<device> intent <op_id>]' and close the op as applied or failed). Narrow 'uncertain' in execRun to cases where the request may have started (timeout, connection reset, 5xx) and map 405/413/429 to a failure that is safe to retry.


**Verified fix:** Give push a deadline (for example 90 s from request start). Once exceeded, answer the remaining ops with a distinct retryable code (RETRY_LATER) without calling begin. Return a distinct status (for example 'uncertain') instead of 'failed' for EXECUTION_UNCERTAIN so clients cannot loop on it. Add a resolver in SQL/cron or on read: for 'uncertain' ops older than about 10 minutes, look for compliance.submissions.raw_input containing '[ai-link px-sync:<device> intent <op_id>]' (buildRunInput's note format) and close the op as applied or failed. In index.ts narrow 'uncertain' to cases where the request may have started (timeout, connection reset, 5xx) and map 413/429/405 to a retryable 'unavailable'.

## [MAJOR] sync-semantics:SYNC-04  supabase/functions/projexa-sync/handler.ts  (559-561, 672-678; src/lib/pipeline/error-codes.ts 74-82, 308-316; src/lib/pipeline/executor.ts 2053-2055)

**Issue:** The handler's TRANSIENT_CODES set does not contain the pipeline's real transient failure codes (BACKEND_UNAVAILABLE, UPSTREAM_TIMEOUT), so a database or connection hiccup is recorded as the permanent, terminal status 'rejected'; for an ambiguous failure (connection lost around COMMIT) the write may exist while the ledger says rejected.


**Scenario:** A pooled-Postgres connect timeout or a 25 s statement timeout is thrown inside an executor. executeTask's catch (executor.ts 2053-2055) turns it into BACKEND_UNAVAILABLE or UPSTREAM_TIMEOUT, runLinkIntent returns failed with that code, the exec answers status failed. In handler.ts 673-675 needsServer=false and transient=false, so finish('rejected') is called; no hold() is applied. begin then answers every re-send of that op_id as duplicate/rejected (0681 140-143). The user's edit is dropped as if the server had refused it for a business reason, although nothing was wrong with it, and a later op on the same record is not held (rejected does not hold) so it applies out of order. If the error was a reset during COMMIT, the record was written but the op is permanently reported as rejected.


**Evidence:** TRANSIENT_CODES = INTERNAL_ERROR, DB_UNREACHABLE, NOT_CONFIGURED, SYNC_NOT_AVAILABLE, CLAIM_UNAVAILABLE, BAD_CLAIM (handler.ts 561) are exec-level names; the pipeline vocabulary (error-codes.ts 74-82) says 'what went wrong on our side: BACKEND_UNAVAILABLE, UPSTREAM_TIMEOUT, INTERNAL_ERROR' and normaliseThrownError (308-316) emits BACKEND_UNAVAILABLE/UPSTREAM_TIMEOUT for transport and statement-timeout errors. The only transient test uses INTERNAL_ERROR (push test 257); a grep for BACKEND_UNAVAILABLE or UPSTREAM_TIMEOUT under supabase/functions and the sync tests finds nothing.


**Suggested fix:** Invert the default: only a closed allow-list of definite business refusals (the 4xx vocabulary: validation, RECORD_NOT_FOUND, ALREADY_RECORDED, NOT_PERMITTED, ...) may become 'rejected'. UPSTREAM_TIMEOUT (statement cancelled, rolled back) -> 'failed'/retry. BACKEND_UNAVAILABLE and INTERNAL_ERROR are ambiguous about whether COMMIT landed -> 'uncertain' with the resolution path of SYNC-05 rather than 'failed, may re-run'. Add a test that iterates PIPELINE_ERROR_CODES and fails when a code is unclassified.


**Verified fix:** Add BACKEND_UNAVAILABLE and UPSTREAM_TIMEOUT to the transient set (map to 'failed' plus hold()). Make that list the same one as RETRYABLE_ERROR_CODES, or add a test that imports RETRYABLE_ERROR_CODES and fails if any member is missing from the handler's set. Only a closed allow-list of definite business refusals should become 'rejected': the 4xx vocabulary such as validation codes, RECORD_NOT_FOUND, ALREADY_RECORDED, NOT_PERMITTED, REQUEST_REJECTED, TOTAL_MISMATCH, BOQ_SEALED and DUPLICATE_ITEM_CODE. Any unknown code should default to 'failed'+hold (retryable), not 'rejected'. I would not move BACKEND_UNAVAILABLE or INTERNAL_ERROR to 'uncertain' as suggested: that is a dead end until SYNC-05 has a resolve path, and the existing INTERNAL_ERROR handling already treats them as re-runnable. Add push tests where the scripted exec returns BACKEND_UNAVAILABLE and UPSTREAM_TIMEOUT and expect status 'failed', the ledger 'failed', and a re-send that runs again.

## [MAJOR] tenant-and-role:TI-2  supabase/functions/projexa-sync/handler.ts  (278-301 (attest), 289 (payload); sign.ts 20, 53-55, 87-91)

**Issue:** The peer attestation token is a plain bearer statement with no holder binding. The payload is {typ,v,sub,org,projects,view,iat,exp}. There is no device or public-key (cnf) claim, and /attest does not even read its request body, so no client can register a key to prove possession. Signed rows also do not bind the view class (itemMessage = px2|org|project|kind|id|version|updated_at|hash(data)). Peer isolation therefore rests entirely on the peers' own handshake code, and anyone who has seen a token can replay it for 24 hours.


**Scenario:** A and B are two 'member' (rank 2) laptops in org-a and have the same view class, since both hide all money. A leads private project proj-priv. B cannot read it: the server answers B's /pull for proj-priv with 404, and proj-priv is not in B's token. During a normal peer handshake A shows B its token (projects includes proj-priv, view = the shared class). B keeps it and, within 24 h, presents A's token to C (another laptop holding proj-priv rows). C checks the signature (valid), org (equal), view (equal) and that proj-priv is in token.projects (yes). Nothing ties the token to A's device, so C hands B the signed proj-priv rows, and B has them without the server ever authorising it. The same replay works after A is deactivated, demoted or removed from the private project, until exp (24 h, accepted by the owner for R2). A row signed for one view class also verifies for any class because the class is not in the signed message, so a receiver cannot tell that a row was redacted for a different class than its own. After a role change, rows already synced stay on the laptop unchanged (the keyset pull only re-sends rows whose updated_at moved) unless the client re-pulls on a view_class change, which this diff does not enforce.


**Evidence:** handler.ts:289 `signing.signToken({ typ: "px-peer", v: 1, sub: user.id, org: user.org_id, projects, view, iat, exp })`; the attest function (278-301) never calls req.text()/json(). sign.ts:87-91 signToken signs the payload as given, and sign.ts:53-55 itemMessage has no view field. The attestation test (keys-ids test 280-299) asserts only the payload fields, signature and TTL, with no possession proof.


**Suggested fix:** Let /attest take the laptop's ephemeral public key (generated per install or device) and put its thumbprint in the token as `cnf`. Peers then prove possession by signing a fresh challenge during the handshake (cheap, no server call, works while the server is down). Add `view` (and `kid`) to itemMessage so a row's signature commits to the class it was redacted for, and keep the receiver-side check `row.view == my view`. Consider a shorter ttl for the `projects` claim, or at least send the client a re-pull-on-view_class-change rule in the manifest.


**Verified fix:** Make /attest read a body {device_pub_jwk} (ES256, per-install, non-extractable on the laptop). Validate it as a P-256 public JWK and put its RFC 7638 thumbprint into the token as cnf.jkt. Peers then run a handshake step, which needs no server call and works offline: the verifier sends a fresh random nonce, the holder signs (nonce || verifier-id || its own cnf) with the device key, and the verifier checks that signature against a cnf.jkt-matching public key before accepting the hello. Reject tokens with no cnf. Keep the 24 h TTL (owner-accepted for R2). Add tests: a token replayed without the device key fails the handshake, and a token whose cnf is a different key fails. Optionally add view and kid to itemMessage (a px3 prefix) so a signed row commits to the class it was redacted for, with the matching constant updated on both sides. As a stopgap, shorten the TTL of the projects claim.

## [MAJOR] tests-quality:F02  supabase/functions/projexa-sync/handler.ts  (handler.ts 559-561 and 672-678; projexa-sync-push.pglite.test.ts 253-268, 309; src/lib/pipeline/error-codes.ts 74-81, 403-406)

**Issue:** The push classification sets (NEEDS_SERVER_CODES, TRANSIENT_CODES) are invented in the handler and the tests feed the handler its own codes (INTERNAL_ERROR, FUNCTION_NOT_AVAILABLE, TEXT_TOO_LONG), so they are circular. The pipeline's real retryable codes BACKEND_UNAVAILABLE and UPSTREAM_TIMEOUT (error-codes.ts RETRYABLE_ERROR_CODES) are in neither set, so they fall to 'rejected'. NOT_AVAILABLE_ON_EXEC is never emitted as a code (the edge stub throws text, which normaliseThrownError turns into INTERNAL_ERROR), and DB_UNREACHABLE / CLAIM_UNAVAILABLE are codes of the exec /run route only.


**Scenario:** A laptop pushes update_task; the exec function's database connection times out (CONNECT_TIMEOUT). executor.ts:2054 normaliseThrownError gives BACKEND_UNAVAILABLE, exec answers status failed with that code, execRun maps it to kind failed, and push() stores the op as rejected. The laptop is told it is a permanent refusal, and re-sending the same op_id returns 'duplicate' (rejected) from the ledger without ever running the write again. A transient outage permanently loses the user's edit.


**Evidence:** Probe 1 (stand-in pipeline answering each code, real SQL ledger): BACKEND_UNAVAILABLE first -> rejected, ledger=rejected, resend -> rejected, pipeline calls 1 (never retried). UPSTREAM_TIMEOUT identical. INTERNAL_ERROR first -> failed, resend -> applied. No push test mentions BACKEND_UNAVAILABLE or UPSTREAM_TIMEOUT (grep).


**Suggested fix:** Extract the classification into an exported pure function classifyFailure(code) and add a parity test that iterates PIPELINE_ERROR_CODES (import from src/lib/pipeline/error-codes.ts) and fails when a code has no deliberate class. Expected table: BACKEND_UNAVAILABLE and INTERNAL_ERROR -> 'failed' (ledger failed, resend calls the pipeline again, calls +1); UPSTREAM_TIMEOUT -> 'uncertain' (a cancelled statement may follow earlier committed statements, so do not blind re-run); FUNCTION_NOT_AVAILABLE -> needs_server; business codes (VALUE_REQUIRED, RECORD_NOT_FOUND, ALREADY_RECORDED, REQUEST_REJECTED, NOT_PERMITTED, TOTAL_MISMATCH, ...) -> rejected. Also a test that a stub-thrown Error('NOT_AVAILABLE_ON_EXEC: ...') ends as needs_server (today it becomes INTERNAL_ERROR and is retried forever).


**Verified fix:** Extract an exported classifyFailure(code) in handler.ts. Treat the pipeline's retryable set (BACKEND_UNAVAILABLE, UPSTREAM_TIMEOUT, plus INTERNAL_ERROR, SYNC_NOT_AVAILABLE, NOT_CONFIGURED, BAD_CLAIM) as 'failed' + hold (ledger failed, same op_id re-runs); FUNCTION_NOT_AVAILABLE as needs_server; everything else rejected.
