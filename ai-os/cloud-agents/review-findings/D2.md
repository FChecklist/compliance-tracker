# Review findings assigned to package D2: Push, jobs and release SQL (0680, 0681, 0682)

Source: independent adversarial review of the backend at 098cb977 (six lenses, each finding re-verified). 20 findings, ordered blocker > major > minor. Finding keys are `lens:id` (ids repeat across lenses). Where two findings describe the same defect, fix it once and say so in the report.

## [MAJOR] edge-handler:F-06  drizzle/0681_projexa_sync_push.sql  (134-176)

**Issue:** The 'same (person, op_id) never has two effects' guarantee fails under concurrent identical requests. projexa_sync_push_begin does `SELECT ... FOR UPDATE` on the ledger row, and when no row exists yet two concurrent calls both see nothing; the second INSERT then waits on the first's unique-key claim and, once it commits, takes `ON CONFLICT (user_id, op_id) DO UPDATE SET status='running', error_code=NULL, result=NULL, created_at=clock_timestamp()...` and still returns action 'run'. The upsert has no WHERE guarding against overwriting a 'running' or 'applied' row.


**Scenario:** Same device, two tabs (or a double-click, or a client auto-retry) flush the same outbox at the same moment: two POST /push requests carry op {op_id:'op-9f8e7d6c', function_id:'create_expense', ...}. Both begin calls return action 'run'; the edge runs the exec function twice and the pipeline writes the expense twice. If the second begin executes after the first has already finished, the upsert resets the 'applied' row to 'running' and wipes its stored result, so a later duplicate check cannot protect it either. Kinds such as expenses, progress_claims and interim_bills make a duplicate financially visible.


**Evidence:** 0681 lines 134-136 (lock-select of a row that does not exist yet), 174-176 (unconditional DO UPDATE), 178-179 (always answers run). Note PGlite is single-connection, so the pglite test suite cannot show this.


**Suggested fix:** Insert first, decide after: `INSERT ... ON CONFLICT DO NOTHING RETURNING`, and only the call that actually inserted (or that re-claims a 'failed'/'needs_server' row via `ON CONFLICT DO UPDATE ... WHERE status IN ('failed','needs_server')`) returns 'run'; otherwise re-read the row and answer duplicate/IN_PROGRESS. Alternatively take pg_advisory_xact_lock(hashtext(user_id||op_id)) at the top of the function.


**Verified fix:** At the top of projexa_sync_push_begin, right after v_user is resolved, take PERFORM pg_advisory_xact_lock(hashtextextended(v_user || ':' || v_op_id, 0)). A second begin then waits for the first to commit and sees the 'running' row (IN_PROGRESS). Belt and braces: add 'WHERE platform.projexa_sync_op.status IN (''failed'',''needs_server'')' to the DO UPDATE and, if no row was inserted or updated, re-read the row and answer duplicate/IN_PROGRESS instead of 'run'. Add a two-connection test (real Postgres or two pg clients), since PGlite cannot show this.

## [MAJOR] requirements-coverage:F4  drizzle/0682_projexa_work_jobs.sql + supabase/functions/projexa-sync/handler.ts  (0682:103-155 (projexa_job_claim), esp. 132, 135-136; handler.ts:741-749)

**Issue:** Jobs can only be found by polling, and each poll is expensive: it recomputes the view class (28 hidden_cols lookups) and runs two UPDATE sweeps even when the queue is empty, which is almost always. Offload is rare and by default runs only on the requester's own device, so nearly all polls are wasted.


**Scenario:** The client runner polls /jobs/claim every 20 s when the user was active in the last 5 minutes and every 120 s otherwise, with no backoff on an empty answer (runner.ts: backoff reset to 0 on every successful claim). Per visible hour 30-180 invocations, average 105: about 18.5K per laptop-month, 924K for 50 users, which alone is 1.8x the free quota; about 50 SQL statements per poll, about 175 statements/minute/laptop at the active rate.


**Evidence:** 0682:132 `v_view := public.projexa_sync__view_class(v_org, v_role)` runs before any job is looked at; 0682:135-136 two UPDATE ... WHERE status='claimed' sweeps per call; no wake-up mechanism anywhere in 0682 or handler.ts; runner.ts ACTIVE_POLL_MS 20_000, IDLE_POLL_MS 120_000.


**Suggested fix:** (a) Let the heads/manifest call (F2) carry jobs_pending (one indexed count of queued jobs this person may run) and claim only when true: saves about 100 calls per laptop-hour. (b) Or return next_poll_seconds from claim (for example 300 when the org queue is empty) so the server throttles every client. (c) In claim, compute the view class lazily only when a queued job has visibility 'project' and another requester, and move lease-expiry sweeps to a rare path. (d) If wanted, a Realtime broadcast from enqueue is free but must be coalesced (2M messages/month).


**Verified fix:** Cheapest and biggest: have the poll (or the F2 /heads call) return jobs_pending and next_poll_seconds, and have the client claim only when jobs_pending is true; or return next_poll_seconds=300+ from an empty claim so the server throttles every client. In projexa_job_claim compute the view class lazily (only inside the project-visibility branch) and move the two lease-expiry UPDATEs to a rare path (for example only when a queued job exists or once a minute per org). Client: back off on empty answers (double up to 10 min, reset on a real job or on user activity).

## [MAJOR] sql-production-safety:SQL-05  drizzle/0681_projexa_sync_push.sql  (134-135 (SELECT ... FOR UPDATE, v_had := FOUND), 166-172 (conflict check), 174-176 (INSERT ... ON CONFLICT DO UPDATE ... status = 'running'))

**Issue:** The 'same (person, op_id) never has two effects' guarantee (header, lines 16-18) is not enforced for two concurrent first deliveries. `SELECT ... FOR UPDATE` locks nothing when the row does not exist yet, so two concurrent begin calls can both see no row. The second INSERT waits on the first, then ON CONFLICT DO UPDATE resets the row to 'running' and the function still returns action 'run'. Both callers go on to execute the write.


**Scenario:** One laptop has two tabs, or a service worker plus a page, that both flush the outbox when the browser fires 'online'. Both POST /push with op_id 'op-abc12345' within the same few milliseconds. Interleaving: T1 and T2 both run line 134 (no row); T1 inserts and commits ('running'); T2's INSERT unblocks and its DO UPDATE sets status='running' and created_at=now(). Both return 'run', and handler.ts:648 calls execRun twice, creating, for example, a duplicate progress entry or a second create_project (the daily cap counts running+applied rows, so the 5/day cap is also bypassable by this race). If T2 stalls long enough for T1's finish to land, the DO UPDATE even rewrites an 'applied' row back to 'running'. A sequential retry is handled correctly, because the first begin has already committed 'running'; only the overlapping case is open.


**Evidence:** 0681:134-135 and 174-176 as quoted. handler.ts:609-651 shows begin, execRun and finish are separate RPC transactions per op, so each begin is its own transaction.


**Suggested fix:** Take `PERFORM pg_advisory_xact_lock(hashtext(v_user || ':' || v_op_id))` before the ledger read, or make the claim atomic: `INSERT ... ON CONFLICT DO NOTHING`, check GET DIAGNOSTICS ROW_COUNT, and when 0 re-read the existing row. Restrict the DO UPDATE path with `WHERE projexa_sync_op.status IN ('failed','needs_server')`.


**Verified fix:** At the top of the ledger step (before 0681:134), add `PERFORM pg_advisory_xact_lock(hashtextextended(v_user || ':' || v_op_id, 0));`. It is released at the end of the RPC transaction and serializes begin calls per (person, op). For the limit counts, take a second advisory lock keyed on the user, or accept the soft cap. As defence in depth, restrict the DO UPDATE at 0681:176 with `WHERE projexa_sync_op.status IN ('failed','needs_server')` and check ROW_COUNT, re-reading the row and answering IN_PROGRESS or duplicate when 0. Add a two-connection test (real Postgres, not PGlite) that fires two begins concurrently and asserts exactly one 'run'.

## [MAJOR] sync-semantics:SYNC-03  drizzle/0681_projexa_sync_push.sql  (134-135, 174-176, 199-210)

**Issue:** Idempotency is not safe for two concurrent first-time begins of the same (user, op_id): both are told to run, so the write can be applied twice; push_finish then has no state guard, so a later duplicate finish can overwrite 'applied' with 'failed', which makes the op re-runnable (a third application).


**Scenario:** Both tabs (or a service worker and a page) of one browser flush the outbox when the online event fires and send the same op_id within a few ms. T1 and T2 both run SELECT ... FOR UPDATE: no row exists, so nothing is locked and v_had=false for both. T1 INSERTs and commits; T2's INSERT blocks on the unique key, then takes the ON CONFLICT DO UPDATE branch (legal under READ COMMITTED), resets status to running and returns action 'run'. Both call the exec function and the create or update is applied twice. If request B's exec then fails or times out, B calls finish('failed' or 'uncertain') after A's finish('applied'), flipping the ledger row; begin treats 'failed' as 'nothing was written, may re-run' (154), so the next retry applies it again.


**Evidence:** 0681 lines 134-135 (FOR UPDATE on a non-existent row locks nothing), 174-176 (DO UPDATE has no WHERE status guard and always returns run), 199-210 (finish selects FOR UPDATE then updates unconditionally, no check of the current status). The test 'the same op sent again is a duplicate' only exercises sequential calls.


**Suggested fix:** First statement after resolving the user: PERFORM pg_advisory_xact_lock(hashtextextended(v_user||':'||v_op_id,0)) so the SELECT and INSERT are serialised per op. Or INSERT ... ON CONFLICT DO NOTHING, read ROW_COUNT, and branch on the existing row. Restrict the DO UPDATE to WHERE status IN ('failed','needs_server'). In push_finish only allow transitions from 'running' (and from 'uncertain' to a resolved state): WHERE status IN ('running','uncertain'); never from applied/rejected.


**Verified fix:** Make the first statement after resolving v_user: `PERFORM pg_advisory_xact_lock(hashtextextended(v_user||':'||v_op_id, 0));`. The second begin then waits, sees 'running' and answers IN_PROGRESS. Also restrict the DO UPDATE to `WHERE projexa_sync_op.status IN ('failed','needs_server')`. In push_finish, update only `WHERE status IN ('running','uncertain')`, so a row can never leave 'applied' or 'rejected' and a late finish can resolve an 'uncertain' row. If no row matches, return the stored state instead of raising, so the handler does not turn it into EXECUTION_UNCERTAIN. Add a test that calls finish('failed') on an applied op and expects the ledger to stay 'applied'.

## [MAJOR] sync-semantics:SYNC-05  drizzle/0681_projexa_sync_push.sql  (144-153 (uncertain is terminal); supabase/functions/projexa-sync/handler.ts 574-693 (no time budget), 653-667, 686-689; supabase/functions/projexa-sync/index.ts 58-75)

**Issue:** 'uncertain' is a dead end: no function, route or timer ever moves an op out of it, so every retry answers EXECUTION_UNCERTAIN forever, whether or not the write happened. Several ordinary events lead there (finish RPC fails once, exec call exceeds 25 s, isolate killed mid-batch), and the laptop is told 'failed' even when the op was applied.


**Scenario:** (a) Exec commits the write, then the single projexa_sync_push_finish RPC hiccups: handler 662-667 reports status failed EXECUTION_UNCERTAIN to the laptop although the record was written; ledger stays running, flips to uncertain after 10 min, and stays there (the exec function's own intent path retries finish twice, exec handler.ts 278-285; this path never retries). (b) EXEC_TIMEOUT_MS is 25 s, the same as the database statement_timeout (25 s), so a slow write is a coin flip between UPSTREAM_TIMEOUT and an aborted fetch that is recorded 'uncertain'; the exec keeps running after the abort and may still commit, with nobody left to close the ledger. (c) A push of 50 ops runs sequentially (begin, exec up to 25 s, finish, signedRow pull per op) with no overall deadline; at ~3 s per op it exceeds a 150 s Edge wall-clock limit (plan-dependent, not measured), the isolate dies mid-batch, the in-flight op stays 'running' and becomes uncertain after 10 minutes although it may never have run. In all three cases the laptop can only keep the op stuck in its outbox, or abandon it and re-send under a new op_id, which duplicates a create that did apply.


**Evidence:** begin: status 'uncertain' always returns retry EXECUTION_UNCERTAIN (144-146); the only writer of uncertain besides the handler is the 10-minute lazy sweep inside begin (147-151). No resolve or reconcile function exists in 0681 or any other migration (grep of 'uncertain' finds only those lines). held is a per-request Set (handler 587), so across batches nothing holds later ops.


**Suggested fix:** Add projexa_sync_push_resolve (called by begin for uncertain/stale-running rows older than ~1 min) that looks for the pipeline's own trace: runDirectTask writes note '[ai-link px-sync:<device> intent <op_id>] <fn>' into compliance.submissions.raw_input (link-exec-entry.ts 101) and the task status in pipeline_tasks; task done -> applied, task failed/absent after 10 min -> failed (re-runnable). Retry push_finish 3x in the handler. Give handler.push a deadline (stop at ~100 s, return the unprocessed ops as retry) and keep exec timeout below the statement timeout (e.g. 20 s). Tell the laptop which uncertain ops are safe to re-send (updates guarded by base_version) versus not (creates).


**Verified fix:** 1. Retry projexa_sync_push_finish about 3 times in the handler before reporting EXECUTION_UNCERTAIN. 2. Add a resolve step (a function called by begin, or by the handler, for 'uncertain' or stale 'running' rows older than about 1 min). runSyncOp writes the note `[ai-link px-sync:<device> intent <op_id>] <fn>` into compliance.submissions.raw_input (link-exec-entry.ts:101,151), and the pipeline_tasks status is its trace. A task in 'done' means 'applied' (take the record id from the task result). A failed, blocked or waiting task means 'failed' (re-runnable). No submission row means the run never started, so 'failed'. Caveat: a submission or task stuck 'in_progress' is still ambiguous because the executor may have committed before the bookkeeping ran. Do not auto-rerun that case. Return a dedicated code so the laptop re-fetches the server row and lets the user decide, instead of a blind re-send. 3. Give push a total deadline (stop after about 100 s and return the unprocessed ops as failed/retry, never begun) and keep EXEC_TIMEOUT_MS below the statement timeout, for example 20 s. 4. Let a late finish resolve 'uncertain' (see the SYNC-03 guard).

## [MINOR] edge-handler:F-13  drizzle/0681_projexa_sync_push.sql  (106-115, 167-172; supabase/functions/projexa-sync/handler.ts 596-598, 659-668)

**Issue:** The optimistic-concurrency check is advisory and bypassable. begin compares the head version of the client-claimed `record` (kind, id, base_version) but never ties that record to the params the executor will actually write (v_params is only hashed), the check is optional (omit `record` and no version check happens), and the version is checked at begin while the write happens up to 25 s later with no version predicate in the pipeline. Also the `record_kind` hint and `record.id` chosen by the client are used by the edge for finish and signedRow, and the begin lookup of projexa_record_head is scoped by org, kind and record id but not by project or readability.


**Scenario:** Two laptops edit task T at base_version 4: both begin calls run before either finishes, so neither sees a conflict and the second write silently overwrites the first. A client can also send record {kind:'tasks', id:'<unmodified task>', base_version:<current>} while params target a different task, or omit `record` entirely, and the conflict protection is skipped. A person who knows (not guesses) a record id in a project they cannot read can learn its existence and edit count from the `conflict` answer (`server_version`).


**Evidence:** 0681 lines 167-172 (check only when v_kind IS NOT NULL, head lookup by org+kind+id only), line 131 (params only hashed), handler.ts line 659 `const kind = hint ?? ...`.


**Suggested fix:** Make the executor receive the expected base version and fail the write if the head moved (compare-and-set in the same transaction), derive record kind/id from the registered function's params instead of from the client, and scope the head lookup by project readability.

## [MINOR] sql-production-safety:SQL-07  drizzle/0681_projexa_sync_push.sql  (166-172 (version check) vs 174-179 (returns 'run'); supabase/functions/projexa-sync/handler.ts:609-651)

**Issue:** The optimistic-concurrency check (head version > base_version means CONFLICT) is made in a separate transaction before the write and is not part of the write itself. The ctx passed to execRun contains no base_version, so the executor cannot enforce it.


**Scenario:** Laptop A edits record R at base_version 3 and pushes. begin sees head version 3 and returns 'run'. Before the executor commits its write (a full runDirectTask/pipeline call, tens to hundreds of ms or more), user B updates R through the web app (version 4). A's write then lands on top of B's change as last-write-wins and becomes version 5. A conflict was claimed to be impossible ('nothing written') but was not prevented.


**Evidence:** handler.ts:645-648 (ctx and execRun call) and 0681:178-179 (the ctx content).


**Suggested fix:** Pass base_version and record identity to the executor and enforce `WHERE <head version> = base_version` inside the write transaction, for example by taking `SELECT ... FOR UPDATE` on the head row in the same transaction as the write. At minimum document the window.

## [MINOR] sql-production-safety:SQL-10  drizzle/0682_projexa_work_jobs.sql  (103-155, 132, 135-136; 0678:108-118)

**Issue:** projexa_job_claim is a polling function. Each call computes projexa_sync__view_class unconditionally (28 hidden_cols calls plus an md5) before it knows whether any shared-visibility job exists, and runs two lease-expiry UPDATE statements for the whole organisation. Heartbeat can also shorten a lease: it sets expires = least(now()+60 s, started+5 min) even when the claim asked for up to 120 s, so a 120 s lease is cut to about 61 s on the first heartbeat.


**Scenario:** 50 online laptops polling every 5 s generate about 10 claim calls/s, each doing 28 sub-calls and two UPDATEs. That is waste against a cost-near-zero goal, and the lease shortening makes a legitimate long-running claimant lose its job to another device after 61 s (it then burns an attempt).


**Evidence:** 0682:132 (view_class before candidate search), 135-136 (updates on every call), 179 (least(now()+60s, ...)) versus 118 (lease up to 120 s).


**Suggested fix:** Compute the view class only when a candidate with visibility = 'project' is found (or cache it), run the expiry sweep with `WHERE ... AND lease_expires_at < now()` on a throttled basis, and use greatest(current expiry, least(...)) in heartbeat.

## [MINOR] sql-production-safety:SQL-11  drizzle/0680_projexa_release_registry.sql  (137-147 (validation then cast), 164-197 (loop), 174-178)

**Issue:** Small robustness gaps in projexa_release_register. (1) built_at is validated only by the regex `^[0-9]{4}-[0-9]{2}-[0-9]{2}T` and then cast with ::timestamptz at line 147, so '2026-13-45T00:00:00Z' raises an uncoded 22008 instead of AW400 BAD_MANIFEST. (2) A manifest with a repeated path is not rejected, so files_count/added counters are wrong and the second row of a changed duplicate is silently dropped by ON CONFLICT DO NOTHING. (3) file_no values are burned if a later file in the manifest fails validation after earlier files were inserted, because the whole call rolls back but identity values do not; the comment at 174 promises no holes in the permanent numbers.


**Scenario:** The caller is the Edge function fetching the owner's published manifest, so exposure is low, but the three behaviours differ from what the header (lines 18-20) promises.


**Evidence:** 0680:144, 147, 164-170, 177.


**Suggested fix:** Validate built_at inside a BEGIN...EXCEPTION that maps the cast failure to AW400, reject duplicate paths up front (`jsonb_path_query` / `GROUP BY path HAVING count(*) > 1`), and move the per-file validation before any INSERT.

## [MINOR] sync-semantics:SYNC-02  drizzle/0681_projexa_sync_push.sql  (166-176 (check then ledger insert); supabase/functions/projexa-sync/handler.ts 609-648; src/lib/pipeline/link-exec-entry.ts 148-153)

**Issue:** The conflict check (v_cur > v_base) is a check-then-act across separate transactions: the version is read in push_begin, the write happens later in the exec function with no version predicate and no per-record reservation, so two pushes with the same base_version both pass and the second silently overwrites the first.


**Scenario:** Task t1 is at version 5. Laptops L1 and L2 of the same person (or two colleagues) both edited t1's title offline from base 5 and reconnect at about the same moment. begin(opA): head=5, 5>5 false, ledger row running, action run. begin(opB), a few ms later: head still 5 (A's exec has not written yet, it takes hundreds of ms to seconds: a second Edge function, pipeline submission/task/memory rows), also run. exec A writes, exec B writes: B overwrites A. head ends at 7, both ops report applied, no conflict is ever shown, A's edit is gone. The same hole exists against any concurrent edit made through the web app between begin and the write (window up to the 25 s exec timeout). The 'two laptops of one person' case is exactly the one a conflict rule exists for, and simultaneous reconnect is when both are on the same stale base.


**Evidence:** push_begin reads the head (168), compares (169), inserts a running row (174-176) and returns; it takes no lock that outlives the function and the ledger row is keyed (user_id, op_id), so two different op_ids never see each other. handler.ts calls begin (609) then execRun (648) as separate network calls. runSyncOp passes only function_id/params/ctx to the pipeline (link-exec-entry.ts 148-153); nothing carries base_version into the write.


**Suggested fix:** In push_begin take pg_advisory_xact_lock(hashtextextended(org||':'||kind||':'||id,0)) and refuse (retry RECORD_BUSY, which the handler already turns into hold()) when another ledger row for the same (org, record_kind, record_id) is 'running' and younger than ~60 s; finish clears it. Additionally in push_finish compare head version before and after: if applied_version > base_version+1 return applied with overwrote_concurrent:true so the laptop can surface it. The strongest variant is to pass base_version to the exec and re-check it under SELECT ... FOR UPDATE on the head row inside the executor's own transaction.


**Verified fix:** In push_begin, when v_kind is not null, take `pg_advisory_xact_lock(hashtextextended(v_org||':'||v_kind||':'||v_rid, 0))` before reading the head. Then refuse with action 'retry' and code 'RECORD_BUSY' if another projexa_sync_op row for the same (org_id, record_kind, record_id) has status 'running' and created_at newer than about 60 s. The handler already turns 'retry' into hold(). The 'running' row is the reservation, and it clears when finish sets 'applied'. Lock plus reservation is enough, because the lock only has to serialise the check and insert. To also catch web-app edits in the window, pass base_version to the exec and re-check the head under SELECT ... FOR UPDATE inside the executor's own transaction. As a cheap detector, have push_finish compare head version with base_version+1 and return overwrote_concurrent:true when it is higher.

## [MINOR] sync-semantics:SYNC-11  drizzle/0682_projexa_work_jobs.sql  (51 (cancelled status), 91-94 (cap), 135-136 (sweeps), 240-245 (job_get))

**Issue:** Lease expiry is only applied inside projexa_job_claim and only for the caller's organisation, so a dead lease is never noticed unless some device of that organisation claims; queued jobs have no TTL and cannot be cancelled ('cancelled' is declared but no function sets it); the 30-open-jobs cap counts jobs whose lease already expired.


**Scenario:** A claimant laptop dies mid-job. The requester polls projexa_job_get: it keeps answering job_status 'claimed' (no expiry check on read). Until some device in the org calls claim the job is neither re-queued nor failed, and it still counts toward the person's 30 open jobs. 30 such or unclaimable queued jobs (for example a type no device of that person supports) make enqueue answer JOB_CAP indefinitely, with no way to cancel them. It self-heals only when someone claims.


**Evidence:** Sweeps at 135-136 are the only code that changes an expired claimed row; enqueue's cap query (91-94) filters on status IN ('queued','claimed') only; job_get (240-245) is a plain select; grep shows no UPDATE ... 'cancelled'.


**Suggested fix:** Factor the sweep into a function and call it from job_get and enqueue (and have the cap ignore expired leases); add a TTL for queued jobs (e.g. 24 h -> failed EXPIRED) and a projexa_job_cancel; schedule the sweep with pg_cron so it does not depend on a claimant.

## [MINOR] sync-semantics:SYNC-13  drizzle/0681_projexa_sync_push.sql  (106-115, 167-172)

**Issue:** The conflict rule is opt-in and not tied to what the function actually writes: record is optional and its kind/id are whatever the laptop says, so an op without record, or with a record naming a different row than params.taskId, is never checked; and the check ignores the op's project, so it answers server_version for any record of the organisation.


**Scenario:** A stale or buggy client sends update_task for taskId t1 with record {kind: tasks, id: t-other, base_version: 0} (or no record): v_cur is read for t-other, the conflict check passes, and t1 is overwritten. Separately a person can send base_version 0 with the id of a record in a private project they cannot read and get action conflict with server_version, which discloses that the record exists and how many real changes it has had (content is not leaked: signedRow is scoped to the op's project). This is inside one organisation, but it is a role-visibility leak.


**Evidence:** v_kind/v_rid come only from p_op -> 'record' (106-114); v_cur is read from projexa_record_head by (org, kind, id) with no project filter (168); the tests always pass a matching record (push test 63).


**Suggested fix:** Derive or validate the target server-side (registry metadata saying which param holds the record id), require record for every function that updates an existing record, and filter the head lookup by project_id = v_project.

## [MINOR] tenant-and-role:TI-1  drizzle/0681_projexa_sync_push.sql  (166-172 (conflict check), 183-212 (push_finish); supabase/functions/projexa-sync/handler.ts 598, 631-636, 653-669)

**Issue:** A pushed op's base-version check and the finish step read the head version of ANY record (kind, id) in the person's org, with no check that the record belongs to the project the op was bound to. This is a version/existence oracle on records in private projects the person cannot read. The conflict reply returns the number even though the signed row comes back null.


**Scenario:** Fixture of projexa-sync-push.pglite.test.ts: u-mem (member, rank 2, org-a) cannot read proj-priv. Task 'tp' lives in proj-priv, and its head row exists (version 1) because it was inserted after the 0679 triggers were installed. u-mem POSTs /push with ops:[{op_id:'op-probe-0001', function_id:'update_task', project_id:'proj-a' (public), params:{taskId:'t1',title:'x'}, record:{kind:'tasks', id:'tp', base_version:0}}]. begin passes the function and rank checks, passes ai_work_link__bind on proj-a, takes v_kind='tasks', v_rid='tp', then looks up h.version for (org-a, tasks, tp) = 1. Since 1 > 0 it returns action 'conflict' with server_version 1. handler.ts:634-635 calls signedRow with project 'proj-a', which returns null because pull_ids scopes to proj-a, but the response still carries {status:'conflict', version:1, base_version:0, server:null}. The person has learned that record 'tp' exists in their org and has been written N times (kind 'project' works the same for a private project's id). A deleted record answers the same way (the test at lines 242-249 shows deleted records answer conflict). Second path: for an op whose executor returns no record id, handler.ts:659-661 sends the client's own rec.kind / op.record_kind and rec.id to projexa_sync_push_finish, which stores and returns projexa_record_head's version for that (kind, id) (0681:203-206) and the handler returns it as `version` (handler.ts:669).
