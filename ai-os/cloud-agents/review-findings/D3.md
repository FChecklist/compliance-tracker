Source: independent adversarial review of the backend at 098cb977 (six lenses, each finding re-verified). 31 findings, ordered blocker > major > minor. Finding keys are `lens:id` (ids repeat across lenses). Where two findings describe the same defect, fix it once and say so in the report.

## [MAJOR] requirements-coverage:F11  supabase/functions/projexa-sync/handler.ts + drizzle/0677/0679 pull  (handler.ts:216-232 (manifest view_class), 410-415 (page has no view class); client replica.ts / sync-client.ts:197)

**Issue:** Role-based visibility is enforced when a row is sent but nothing makes a laptop re-evaluate rows it already holds when the person's role or the organisation's cost-visibility setting changes. The server returns view_class in the manifest, the client parses it and never uses it (grep: no use in lf-client-core, lf-pwa-offline, local-first-complete), and the pull cursor moves only by updated_at, which a role change does not touch.


**Scenario:** A manager is demoted to member: the laptop keeps every money/wage/credit_limit value it already pulled, readable offline forever. A member is promoted: previously pulled rows keep NULL money columns until each row happens to change. Both break 'a user sees their own data as per role', which the owner called non-negotiable.


**Evidence:** sync-client.ts:197 only copies view_class into the parsed manifest; replica.ts has no reference; the page returned by buildPage (handler.ts:410-415) carries hidden_fields and redacted but not the class it was redacted under.


**Suggested fix:** Backend: put view_class and org_view_class in every page and in the heads call so a laptop can store it per (project,kind) and compare cheaply, and document that a change forces a cursor reset and local purge of that pair. Client (not in diff): reset cursors and re-pull when it changes. Add a test: change a role, assert the manifest class changes.


**Verified fix:** Client (required, not in this diff): store {view_class, org_view_class} from the manifest per organisation; when either differs from the stored value, null every pair cursor for the affected projects/kinds, purge or re-pull the non-dirty rows of those pairs, then store the new class. Backend (small): add view_class and org_view_class to every pull page (buildPage, handler.ts:407-415) so a page is self-describing and the client can reject or restart a pass if the class changed mid-pass. Test: change a user's role and the cost_visibility setting, assert the manifest class changes and the page class matches.

## [MAJOR] requirements-coverage:F2  supabase/functions/projexa-sync/handler.ts + drizzle/0679_projexa_record_versions.sql  (handler.ts:337-373 (pull), 419-446 (changes); 0679:355-414 (projexa_sync_changes))

**Issue:** The backend only offers a per-project head (one /changes call per project) and a per-(project,kind) pull. It has no one-call 'what changed anywhere' and no per-kind head, so a laptop that sees any project head move must sweep every (project x kind) pair. At the owner's top priority (cost near zero) the design exceeds the Supabase free quota at 1 to 12 laptops.


**Scenario:** P=5 projects, K=28. The shipped replica (projexa feat/lf-client-core replica.ts run(): 1 manifest, then a /pull for EVERY pair even when nothing changed, then /changes per project) costs 1 + 5x28 + 5 = 146 invocations per pass, plus 10 more once org kinds are consumed. The c1 scheduler (server-step.ts) checks each project head first (5 calls per tick) but runs the whole pass as soon as ANY of the 5 heads has moved. In a 50-person org that is nearly every 5-minute tick, and a laptop's own pushes move the heads too. Result: about 1,800 calls/hour/laptop when active (317K per laptop-month, 15.8M for 50 users) or 60/hour when completely quiet (528K for 50 users, already over 500K). Also the per-person cap of 120 requests/minute per isolate (handler.ts:171) is below the burst of 146 requests of one pass at concurrency 2, so some requests get 429, which is still an invocation and is retried.


**Evidence:** 0679:393-396 head is max(seq) for one (org, project) only; the manifest has no heads; handler.ts:171 limiter counts requests but every rejected request is still invoked; replica.ts lines 482-517 (pair sweep) and 522-533 (changes per project); server-step.ts per-project head loop then `o.sync()`; cadence scheduler.ts DEFAULTS baseMs 5 min. The change log already names kind + id + version + op for every change (0679:398), so after the first pull the keyset sweep is redundant except for rows that predate tracking.


**Suggested fix:** Ranked by saving. (1) Biggest, about 97-99 percent of pass calls: add one cheap call (new POST /heads, or extend /manifest) returning {heads:{<project>:head_seq,'__org__':head_seq}, projects_etag, view_class, org_view_class, release:{current,min_compatible}, jobs_pending}: one grouped index-only query on projexa_change_log(org_id,project_id,seq) over the readable projects, about 5 statements. Add a multi-project /changes ({projects:[{id,after_seq}] up to 50}) so one call returns every moved record with kind+id. The client then fetches only the named ids and runs the keyset sweep and /ids only on first install, schema bump or weekly. (2) CORS Max-Age 7200 (F3). (3) Jobs wake-up via jobs_pending instead of polling (F4). (4) /ids reconcile weekly or by digest (F6). (5) Batch exec (F8). (6) Light release gate (F7). (7) Return org_id from the pull RPC so orgOf stops re-running the manifest (F13). (8) Set-based row builder (F12). (9) Retention (F9). Add per-route invocation counters or a header so R14 can actually be measured.


**Verified fix:** (1) Client (not in this diff, biggest saving, about 95 percent): after a pair has a done marker and the feed is available, pull only the pairs the /changes page names (via pullIds); run the full keyset sweep weekly or on schema bump; skip the pass entirely when the own push is the only thing that moved the head (feed shows only known versions). (2) Backend: add /heads (or extend /manifest) returning {heads:{<project>:head_seq,'__org__':head_seq}} from one grouped query on projexa_change_log(org_id,project_id), and optionally a multi-project /changes; this turns P head calls into 1. (3) Raise REQUESTS_PER_MINUTE to about 600 (it is an abuse guard, and 429s cost an invocation anyway). (4) Add a per-route counter or response header so R14 can be measured.

## [MAJOR] sql-production-safety:SQL-04  drizzle/0679_projexa_record_versions.sql  (23-25 (documented limit), 54-67 (seq identity), 144-150 (inserts at trigger time), 355-414 (changes))

**Issue:** The change-log cursor is a bare identity seq assigned when the trigger fires, not when the transaction commits, and readers only look back 200 seq (after_seq - 200, per the header). That window is smaller than the migration's own bulk scenario (a 10,000-row import). The stated fallbacks (the daily /ids reconcile and the 'updated_at keyset pull') do not repair these rows: the keyset pull cannot, because the rows' created_at/updated_at come from now(), which is the transaction START time, and the laptop's cursor has already moved past that timestamp.


**Scenario:** Laptop L has after_seq = S. User A starts a BOQ import transaction; its 10,000 line rows take seq S+1..S+10000 at statement time and stay uncommitted. User B commits one ordinary change, seq S+10001. L polls, sees S+10001, and moves its cursor there. A commits. On the next poll L asks from S+10001-200 = S+9801, so it gets 200 of the 10,000 lines and never sees S+1..S+9800 through the changes path. Those rows have created_at = A's transaction start, which is earlier than the keyset cursor L already holds, so the keyset pull does not return them either. Only the daily /ids reconcile can surface them, so L is stale by up to a day for a colleague's bulk import. That defeats the requirement 'user sees their data'.


**Evidence:** The header concedes the interleaving at 0679:23-25 but sizes the repair at 200 seq. The 10k import statement is at 0679:27. construction-boq-service.ts:419 shows lines are inserted in one multi-row insert per level within one transaction.


**Suggested fix:** Record the writer's xid8 (pg_current_xact_id()) in each log row and have projexa_sync_changes return only rows whose xid8 < pg_snapshot_xmin(pg_current_snapshot()), so the log is gap-free to the reader. Failing that, replace the fixed 200 window with an overlap that covers the longest allowed transaction.


**Verified fix:** Add `xid xid8 NOT NULL DEFAULT pg_current_xact_id()` to projexa_change_log and make the changes cursor (xid, seq). In projexa_sync_changes, order by (xid, seq), take rows with `(xid, seq) > (after_xid, after_seq)` and `xid < pg_snapshot_xmin(pg_current_snapshot())`, and return the cursor as that pair. Every transaction with xid < xmin is complete, so a late-appearing row always has a larger xid than the cursor. Note that one long-lived open transaction anywhere on the shared DB then only delays sync freshness. The cheaper alternative is to drop the fixed 200-row window and overlap by time: re-read changes with `at >= <at of the cursor row> - interval '2 minutes'`, sized above the longest allowed transaction (25 s statement_timeout), and keep the client's version-based dedupe.

## [MAJOR] sync-semantics:SYNC-01  drizzle/0679_projexa_record_versions.sql  (23-26 (documented limit), 54-69 (identity seq), 393-412 (changes); also 0678:207-219 (/ids), 0677:56-64 (cursor_field), src/lib/services/projexa-sync-read.pglite.test.ts:298-306)

**Issue:** The documented mitigation for out-of-order seq commit does not repair a missed UPDATE, and for 22 of the 28 kinds the change log is the ONLY path by which an update reaches a laptop.


**Scenario:** Project P, kind boq_lines (no updated_at, so cursor = created_at and updates never move it). T1 = one multi-statement transaction that rewrites 600 BOQ lines (their trigger rows take seq 7001..7600, invisible until commit). While T1 is open a site engineer's progress entry T2 in P commits with seq 7650. The laptop polls /changes: sees 7650, stores next_seq=7650. T1 commits. Next poll re-asks from 7650-200=7450, so T1's lines with seq 7001..7449 (~450 rate/quantity updates) are never returned. Keyset pull cannot see them (created_at unchanged, and for tables that do have updated_at the txn-start value is already below the cursor). The daily /ids reconcile lists ids only, and the laptop already holds every id, so nothing is repaired. The rows stay stale until someone edits each one again. The 200 is in GLOBAL seq units (one identity for every org and project), so in a busy database it can be only seconds of history. The re-ask rule lives in the laptop code (projexa repo, not in this diff); the server enforces nothing.


**Evidence:** 0679 header 23-26 states the limit and says /ids + keyset repair it. Facts that contradict that: (a) /ids returns bare ids (0678 207-219: SELECT t.id::text only), no version, so a stale-but-present row is invisible to it; (b) manifest cursor_field is created_at for boq_lines, change_orders, rfis, documents (read test 301); schema.ts declares updated_at on only 6 of the 28 tables (projects, pms_issues, construction_boqs, veri_meetings, construction_progress_claims, pms_wiki_pages); (c) changes() returns rows by seq > p_after_seq (401) and next_seq is the last returned seq (411); seq is GENERATED ALWAYS AS IDENTITY assigned at trigger time, not commit time (54-55). The trigger fires per row inside the writer's transaction, so any transaction that is still open when a later one commits creates the gap. Verify live which tables really have updated_at: select table_name from information_schema.columns where table_schema='compliance' and column_name='updated_at'.


**Suggested fix:** Fix it on the server, not in an unenforceable client convention. (1) Add xid xid8 DEFAULT pg_current_xact_id() to projexa_change_log and have projexa_sync_changes serve only rows with xid < pg_snapshot_xmin(pg_current_snapshot()), paging on (xid, seq); then a row can never appear below a cursor that was already handed out. (2) Make /ids return [id, version] pairs (left join projexa_record_head, 0 when untracked) so the daily reconcile also repairs stale versions, and return head_seq with each page. (3) If a client-side overlap is kept, define it in time (re-read the last N minutes by 'at'), not 200 global seqs.


**Verified fix:** Make the feed safe on the server. Add `xid xid8 NOT NULL DEFAULT pg_current_xact_id()` to platform.projexa_change_log. Have projexa_sync_changes return only rows with `xid < pg_snapshot_xmin(pg_current_snapshot())`, ordered and paged on (xid, seq) with an (xid, seq) cursor. Paging on seq alone is still unsafe, because a lower seq can belong to a higher xid. A row can then never appear below a cursor that was already handed out, and the client overlap is no longer needed. Cost: any open writing transaction, DPDP's included, delays the feed until it ends. Also change /ids to return [id, version] pairs (left join projexa_record_head, 0 when untracked) so the daily reconcile repairs stale versions too. A time-based overlap on `at` is not a real fix, because a txn that is open longer than the window is still missed. Add a pglite test that holds two sessions, commits out of seq order, and checks that nothing is skipped.

## [MINOR] sql-production-safety:SQL-01  drizzle/0679_projexa_record_versions.sql (same body re-created in drizzle/0683_projexa_sync_more_kinds.sql)  (0679:79-157 (inner BEGIN at 97, EXCEPTION at 151-154), 0679:174 (FOR EACH ROW trigger); 0683:72-157, 0683:175)

**Issue:** The tracking trigger is an AFTER ROW trigger whose body is a BEGIN ... EXCEPTION WHEN OTHERS block. That opens one subtransaction per changed row, and each one assigns a subxid because it writes to the head and the log. A bulk write therefore runs thousands of subtransactions inside one transaction, and per-row work (to_jsonb of the whole row, sha256, FOR UPDATE on the head, an upsert, a log insert) is added to the business write path.


**Scenario:** A 10,000-line BOQ import (the header's own example at 0679:27) is one TenantDb transaction doing multi-row inserts (src/lib/services/construction-boq-service.ts:404-419). It fires the trigger 10,000 times and creates about 10,000 subxids. PostgreSQL caches only 64 subxids per backend (PGPROC_MAX_CACHED_SUBXIDS), so after 64 this backend is flagged suboverflowed. While the import runs, every concurrent snapshot, including the DPDP product's on the same database, is marked suboverflowed and has to resolve xids through pg_subtrans for tuples written by recent transactions. The import also gets slower by roughly 10,000 x (jsonb conversion + hash + 3 index probes + head upsert + log insert), which lengthens the transaction.
