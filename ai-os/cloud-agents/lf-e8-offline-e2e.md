## Why
The owner's order: the laptop is the daughter server, it works with NO internet and with OUR server down, the person stays signed in, the app is not deleted by the browser. `e2e/offline-local-first.spec.ts` (four tests: R1 offline, R2 server down, R9 logged in forever, R10 persistent storage + release put back) is the ONLY test that proves this in a real browser, and it has NEVER PASSED: it was written on a laptop that cannot run a production build and a browser together. Its first CI run (GitHub Actions run 36995579578, job "Offline e2e (local-first)") failed all four tests at the same step: `getByTestId("prepare-percent")` not found, because nothing in the app ever turned the `px-local-first` flag on. That product bug is fixed in `993571ea` (`<LocalFirstDefault/>` in `src/app/(app)/layout.tsx`, see `docs/local-first/CONTRACT.md` "Default ON for a signed-in person"). Everything after that first step has never run. Your job: make the four tests pass in a real Chromium, honestly.

## Do
1. Set up exactly like CI (`.github/workflows/ci.yml`, job `Offline e2e (local-first)`): `bun install --frozen-lockfile`, `bunx playwright install --with-deps chromium`, then `bunx playwright test -c playwright.local-first.config.ts`. The config builds a production build against a local Auth stand-in (`e2e/support/fake-supabase-server.mjs`), runs `node scripts/make-release.mjs`, and starts `next start`; the sync service and every `/api` call are answered inside the browser by the spec (`page.route`). If Turbopack refuses the build in your sandbox use `LF_LOCAL_BUNDLER=webpack`. Build once, then iterate on single tests (`-g "R1"`) to save time.
2. Run it. For every failure, find the REAL cause by reading the error context, trace, screenshot and the page's console. Two kinds of cause, treated differently:
   - **An app bug** (the product does not do what the requirement says): fix the app, and add or extend a unit/component test that FAILS without your fix (planted-bug rule: break the fix in a copy or an injected wrong dependency, show the test fails, restore). Never edit a security check in place to "plant" anything (PREAMBLE).
   - **A stale or wrong spec/stub** (the spec answers the sync service in a shape the real service no longer uses: compare with `docs/local-first/CONTRACT.md` and `supabase/functions/projexa-sync/handler.ts` in the compliance-tracker clone; e.g. the manifest's `user` must carry `auth_user_id` equal to the sign-in id, `/heads` exists, `/pull` rows are `{id, updated_at, version, data, sig}`): update the spec/stub to the real shape.
3. **Never weaken what a test asserts**: no longer timeouts to hide a hang, no deleted assertion, no skipped test, no `retries`. A wait may be lengthened only when you show (with the trace) that the app legitimately needs the time; say so in the report. Each test keeps its intent: R1 the app opens and the BOQ shows from the laptop's own database with the network OFF, an edit made offline waits and is sent exactly once when the network is back; R2 internet up but OUR server (sync service and /api) refused: the app keeps working, the edit waits and syncs when the server is back; R9 once signed in the person is not sent to /login after a lost cookie and a dead sign-in service; R10 the app asks for persistent storage and puts the release back if its cache is missing.
4. When all four pass, run the whole config TWICE in a row from a clean build state: both must be green (flakiness is a failure). Then run the unit tests of every file you touched (one file at a time), a restricted `tsc` over the changed files, and `bunx eslint` on them.
5. Real findings you cannot fix inside this package (a requirement the app really does not meet, a design question): do not paper over them; list them in the report with the failing step and your diagnosis.
