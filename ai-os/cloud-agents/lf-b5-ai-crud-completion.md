## Goal (owner requirement R7)
"The external AI and the internal AI can make the complete project, edit, delete, update, etc. for that user as per role and its organisation." Package B2 did everything the app already has a SERVICE for. It left two classes undone; finish both, with the same discipline (every AI function runs the SERVICE the app's own route runs, never a second write path):

### Class 1: organisation-scoped records (B2: "needs an owner decision": the owner delegated it: decide, document, build)
BOQ categories, and the other organisation masters the app lets a person manage (vendors/suppliers, customers, companies, departments; currencies and exchange rates are money: rank 3, level 2 only). A link is bound to ONE project, so the id rule of the link cannot hold an organisation record. Design an organisation-scoped function class: read how the user-wide link (0668) resolves the person and organisation, and make organisation functions usable ONLY through a link whose person has the required organisation role (`ai_work_link__role_rank`: rank 3 or higher unless the app's own route allows lower), take ids of organisation records verified against the person's organisation (never accept an id of another organisation: `RECORD_NOT_FOUND`), be level 2 (a draft the person confirms, or direct when their per-person switch is on) for every delete/rename/merge, and show the blast radius in the draft card (a category rename rewrites the lines of every project of the organisation: say how many). Create/update/archive/delete only what the app's routes/services already offer for each master; do NOT invent rules the app does not have.

### Class 2: the eight edits and deletes that have no service yet (B2's list)
`update_activity`, `update_progress_category`, `update_attendance`, `delete_attendance`, `update_change_order`, `cancel_change_order`, `update_boq_line` (description and unit; money stays where it is), delete of a project meeting. For each: build the missing SERVICE function (in the existing service file for that module) with explicit, conservative rules, expose it as a registry function the same way B2 did, and write the decision into `ai-os/AI_CRUD_COVERAGE.md` so the owner can veto. Defaults to use (document each):
- attendance: edit/delete only by a manager (rank 3) and only for the last 7 days; every delete writes an audit row through the existing activity-log service; labour cost reports recompute from rows (nothing cached is left stale).
- change order: update/cancel only while `draft` or pending approval; cancel withdraws the pending e-signature request(s) in the same transaction; an approved/rejected change order is immutable.
- `update_boq_line`: description and unit only, only while the BOQ is not approved/locked; quantity, rate, amount are never changed here.
- project meeting delete: soft delete (additive column or status, in migration 0687, with a down file); readers hide soft-deleted rows; the sync kind `meetings` must emit a tombstone (check the tracking trigger in 0679/0683 handles it).
- `update_activity` / `update_progress_category`: names, dates, weights; refuse a change that would orphan existing progress entries or break the weight sum, with a clear message.
- NOT in scope (record as owner decisions, do not build): `delete_drawing` (it removes a stored file with the service-role storage client, which the exec function does not have), approving one's own submission or a claim, invoicing.
