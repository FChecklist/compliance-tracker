## Goal
An independent review found that the version / change-feed machinery (which is how a laptop learns what changed) can silently miss updates, costs more than it should per page, has no retention (it would fill a free-tier database), and that several test claims cannot fail. Fix it, in this order: (1) missed updates (sql:SQL-04, sync:SYNC-01: the sequence is assigned when the trigger fires, not when the transaction commits, so a reader can pass a seq whose transaction commits later; for 22 of 28 kinds the change log is the ONLY path an update reaches a laptop. Use a commit-order-safe cursor, the standard pattern is recording the transaction id and reading only rows older than the oldest in-flight transaction (`pg_current_xact_id()` / `pg_snapshot_xmin(pg_current_snapshot())`), or an equivalent you can prove with a deterministic test), (2) tombstones and moves (sync:SYNC-07), (3) retention (sql:SQL-06, sync:SYNC-10, requirements:F9), (4) cost per page and per poll, (5) the rest and the test-quality items.

## Hard design requirements
1. **Cost near zero is the owner's first priority** (then ease, then security; org isolation and role-based visibility are non-negotiable). The tracking trigger runs on every write of hot tables (`compliance.users`, `compliance.documents`, ...): it must never block or slow a business write noticeably, must never fail one, and its cost per row must be small (sql:SQL-01, sync:SYNC-06, requirements:F17). Report measured statement/row costs before and after where you change them.
2. **No silent total failure** (sql:SQL-08): provide a health check the deploy runbook can call (a SQL function that proves tracking works for every kind: writes a probe row inside a rolled-back transaction, or compares counts) and test it by breaking tracking.
3. **Retention**: each append-only table gets a prune function with a documented, conservative retention (change log: bounded by time and by the oldest laptop that could still resume; a laptop older than the window must be told to do a full resync rather than silently miss deletes). Do NOT schedule cron jobs in a migration; provide the functions and say in the report how they should be wired (the owner's existing daily mechanism), counting the free-tier cost.
4. **Versions survive rollback and replay** (sync:SYNC-09): give versions an epoch (or an equivalent) so that rolling 0679 back and re-applying cannot make a laptop believe an old version is current.
5. **Role change** (requirements:F11): data already on a laptop must be re-evaluated when the person's role or the organisation's cost-visibility setting changes. The server's part: the view class travels with every page so the laptop can detect it cheaply, and the change feed or manifest says what to drop/refetch. Describe the laptop's part precisely in the report (the client engineer will implement it).
6. **Hash vs projection** (sync:SYNC-14): the version's content hash must correspond to what a laptop actually receives, or a change to an unsent column must not bump the version; decide, justify, test.
7. Keep every route/response shape backward compatible unless a finding requires otherwise; document any new key.
