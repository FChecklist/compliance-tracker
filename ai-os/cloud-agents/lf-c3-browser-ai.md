# Package lf-c3-browser-ai (laptop app, repo projexa)

Branch `claude/lf-c3-browser-ai` from `origin/feat/lf-client-core` if it exists, else `origin/feat/local-first-complete`.

## Goal (requirements R5, R6, R8, R11, R12)
The user's own AI that lives in their browser (Chrome, Edge, Safari, with built-in or extension assistants) can AUTOMATICALLY work with PROJEXA for that logged-in user on that laptop, with nothing for the user to set up and nothing for them to think about, acting on the LOCAL database as that person with their role; and NO AI can change the software itself.

## Build under `src/lib/local-first/ai/`
1. `api.ts`: `window.projexa.ai` = a small, documented, async API:
   - `manifest()` (who the person is, role, organisation, projects, which kinds and functions are available), `list(kind, {projectId, filter, limit})`, `get(kind, id)`, `search(text, {projectId})`;
   - the WRITES `create` / `update` / `delete` as named functions that go through the local outbox (`src/lib/local-first/outbox.ts` on `origin/feat/lf-client-core`: enqueue with functionId/params/record base version and the optimistic local change) so they work offline and sync later;
   - every write is checked LOCALLY first against the person's role rank and the function registry the server exposes (the same function ids and `min_role_rank` as the AI work link: read compliance-tracker `origin/feat/lf-sync-backend` `supabase/functions/ai-work-link/function-registry.generated.json`), refuses what the role may not do with a plain-words error, and DELETES return a draft the PERSON confirms with one click unless the person has the "let my AI act without asking" setting (read it from the manifest if present; default off). The server remains the authority on push.
2. `manual.ts`: a machine-readable manual (JSON) and a plain-words one: what the AI may read and do, the function list with parameters, the role rules, and the explicit statement that the software cannot be changed. Served four ways: `window.projexa.ai.manual()`, a static route `/ai-manual.json` and `/llms.txt` (static, force-static, no server data), an in-page `<script type="application/json" id="px-ai-manual">`, and accessible labels / ARIA roles on the main controls so DOM-driven browser agents can operate the UI.
3. `webmcp.ts`: when `navigator.modelContext` (WebMCP) exists, register the same tools (list/get/search/create/update/delete/manifest) with schemas; feature-detected, silent when absent.
4. Immutability (R5): the AI surface exposes NO function that writes code, files, the service worker, the release bundle, the cache or the app configuration. Add a guard test that enumerates every exposed tool/function name and fails if one matches a deny-list (code, script, eval, file, cache, serviceworker, bundle, release, config). At startup verify that the installed release files still match their recorded sha256 (use the release file table in the local database meta if present from `origin/feat/lf-pwa-offline`: `src/lib/local-first/release/*`; if absent, define the narrow interface and list the integration step). The page must not expose eval-like entry points.
5. Auto-attach with zero setup: the API is registered on every authenticated page of the app shell (and on the static `/local` shell from `origin/feat/lf-pwa-offline`) as soon as the person is logged in. Document in `docs/local-first/BROWSER_AI.md` how each kind of browser agent finds it (WebMCP tool registry; `window.projexa.ai`; `/llms.txt`; the manual script tag; ARIA) and what each can do.

## Tests
Unit tests for every API function against the fake sync server fixture (`src/lib/local-first/__fixtures__/fake-sync-server.ts` on `origin/feat/lf-client-core`) and a fake local database: a role matrix (viewer / member / manager / admin) for create/update/delete; deletes become drafts; offline writes queue; the manual lists exactly the functions the role may use; the deny-list guard; WebMCP registration with a fake `navigator.modelContext`; a tamper test (a modified file hash -> the surface disables itself and reports).
PLANT: role check skipped; delete executed without a draft; a deny-list name added to the tool list; hash mismatch ignored; each must be caught.
