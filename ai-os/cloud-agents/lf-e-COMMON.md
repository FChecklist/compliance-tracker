# Wave 2 laptop-app packages: common rules (read after PREAMBLE.md, before your own brief)

These packages work in the **projexa** repository (the laptop app), base `origin/feat/local-first-complete` (it already contains the client sync engine, the offline shell and release bundle, peers, jobs and browser-AI, merged and type-checked). Your branch is `claude/<package id>` created from that base: `cd` into the projexa clone, `git fetch origin`, `git checkout -B claude/<package id> origin/feat/local-first-complete`. Briefs and the backend are in the other clone (compliance-tracker, branch `origin/feat/lf-sync-backend`): read `supabase/functions/projexa-sync/README.md` and `ai-os/PROJEXA_LOCAL_FIRST_REQUIREMENTS.md` there for the server side.

Read in projexa first: `docs/local-first/CONTRACT.md` (the laptop <-> backend contract), `docs/local-first/ROUTE_TABLE.md` (how a module is added to the offline shell), `docs/local-first/PWA_OFFLINE.md`, `docs/local-first/` (every file), and the code you will touch.

## What the owner asked for (the point of all this)
The user's laptop is a daughter server: the whole app and the whole database of the person and their organisation (as per role) live on the laptop, work with NO internet and with OUR server down, sync two ways with Supabase and laptop to laptop, and cost the owner nothing (Vercel and external servers ~zero). The person never has to think. Priority: cost near zero first, ease of work second, security third. Organisation isolation and role-based visibility are non-negotiable: a person sees only their organisation's data as per role.

## Module-conversion rules (packages E2-E5)
A "module" is a screen family of the online app (`src/app/(app)/<module>/...`). Converting it means: it opens and works from the laptop's own database with the network off.
1. **Find the real screens first**: read `src/app/(app)/<module>/page.tsx` and the client components it uses; list every screen (list, object, create, entry, export) and exactly which data each shows. Put this list in your report.
2. **Map data to replica kinds**: the replica carries 28 project kinds and 9 organisation kinds (`supabase/functions/projexa-sync/handler.ts` in compliance-tracker: `SYNC_KINDS`, `ORG_KINDS`). The laptop receives a CURATED projection of each record (`ai_work_link__records_core`, role-redacted: money fields are hidden below a role), so a screen may need a field the sync does not carry. NEVER invent or fabricate a value: show what is on the laptop, say plainly what is not, and list every such gap under GAPS in your report (the backend engineer will close them). Organisation kinds are not consumed by the client engine yet (another package adds them): if a screen needs a master (vendors, departments, ...), take it through a small interface in your adapter and note the dependency.
3. **One adapter + one screen per route + ~10 lines in your cluster file** (`src/lib/local-first/shell/clusters/<cluster>.ts`; the route table already spreads it). Follow `modules/scope-adapter.ts` and `ScopeListScreen.tsx` exactly: the adapter is plain TypeScript, reads only the local database through `loadLocalFirst` (never the server), treats replica rows as untrusted input (filter, never cast), and returns a tagged union (`no_project` / `not_synced` / `local` ...) so the screen says a calm, true thing in each state. No error dialog for being offline.
4. **Writes**: a screen's write goes through the offline write path (`src/lib/local-first/local-writes.ts`, `outbox.ts`, `shell.writer`; see how the RFI create/edit screens use `use-local-writes.ts`) and then through the AI-link push. Only functions that exist in the registry (`supabase/functions/ai-work-link/function-registry.generated.json` in compliance-tracker: ~72 write functions, more coming) can be pushed. Where a registered function exists, wire the write (shown at once as a pending edit, sent when the laptop can reach the server). Where none exists, the screen is read-only offline and says so in plain words; list it under GAPS. **Money and approvals are never computed or decided on the laptop**: send the person's intent and let the server recompute.
5. **Quality bar** (the owner's rule): every behaviour has a committed test that FAILS when the behaviour breaks; after writing a test, PLANT the bug (break the production code), see it fail, restore. Adapter tests run against `fake-indexeddb` (seed the person's database as `modules/scope-adapter.test.ts` does); render tests follow `shell/LocalShell.test.tsx` (network off, `fetch` spy, assert it was never called). Also test: another person's database contributes nothing; a viewer-role person never sees a hidden field; the "not synced yet" state.
6. **Files**: you may create files under `src/lib/local-first/shell/modules/` (names prefixed by your module) and edit ONLY your cluster file in `clusters/`. Do NOT edit `route-table.ts`, `types.ts`, `LocalShell.tsx`, or any client-engine file (`replica*.ts`, `outbox*.ts`, `sync-client*.ts`, `local-db*.ts`, `local-writes.ts`, `local-reader.ts`, `identity.ts`, `sign-out.ts`, `boot.ts`, `release/**`, `peer/**`, `jobs/**`, `ai/**`): other engineers edit those in parallel. If you need a change in one of them, put a thin wrapper in your own file and describe the needed change in the report.
7. Run `bun test --isolate <your files>` one file at a time (the laptop has little RAM; cloud has plenty but be tidy). Typecheck your changed files with a temporary `tsconfig.tmp.json` as in the PREAMBLE, delete it afterwards.

## Final report additions
For every screen: route, kinds read, writes wired (function ids) or read-only, GAPS (fields/functions missing), tests. Never claim more than you verified: nothing here has run in a real browser.
