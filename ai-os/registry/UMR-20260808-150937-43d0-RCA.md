## Root cause (already found and fixed by a prior RCA)

This exact UMR is the **confirmed live incident** cited by name in
`resource_governor.py`'s own `scan_stuck_tasks()` docstring (added by a prior
task, UMR-20260813-101757-f13c):

`scan_stuck_tasks()`'s SIGTERM→SIGKILL stuck-task reaper assumed "status=running"
always means an ephemeral `veridian-worker@<task_id>.service` unit expected to
exit on its own within `STUCK_TASK_TIMEOUT_SECONDS` of *its own* start. That
assumption is false for `task_kind='systemctl_action'` rows whose `unit_name`
is a **persistent, always-on singleton daemon** (`Restart=always`/
`on-failure`, `WantedBy=default.target`) — exactly what
`veridian-superboss-gateway.service` is. `_perform_spawn()` marks a
`systemctl_action` row `status="running"` the instant `systemctl start`
returns 0, including when the unit was *already* active — in which case
`_unit_active_enter_timestamp()` reports whenever the daemon first started,
which can trivially be older than `STUCK_TASK_TIMEOUT_SECONDS`. The reaper
then wrongly concluded the row was "stuck" on its very next tick and
SIGTERM'd (31s after dispatch) then SIGKILL'd+**disabled** (60s later) the
real, healthy, always-on gateway daemon. The unit stayed disabled/inactive
for 5 days until the prior RCA (`UMR-20260813-101757-f13c`) caught and fixed
it.

## Fix (already merged — no new code change needed here)

`veridian-scripts` PR #296, commit `41c3d02ca77feeeac6477de4836dbd2f0667ded8`
(title: `fix(resource_governor): scope stuck-task SIGTERM/SIGKILL scan to
veridian_task_create rows only`). Live-reverified in this task:

  (`git merge-base --is-ancestor` confirmed).

  `systemctl_action` rows never enter it, since `_perform_spawn()` already

- `veridian-superboss-gateway.service` is confirmed **live, right now**:
  `enabled`, `active (running)` since `2026-08-13 11:05:55 UTC` (per
  `systemctl --user status`).
