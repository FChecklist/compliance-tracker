# ai-work-link-exec (PROJEXA-BUILD-002 WP-09b)

The executor of the Universal AI Work Link. `ai-work-link` records an intent (a direct action, or a draft the person confirmed); this function CLAIMS it, runs it through the real pipeline as the person, and stores the outcome on the intent. It is deployed and switched OFF: while `platform.ai_work_link_settings.writes_enabled` is false nothing here changes project data, and while its two owner-set settings are absent every request answers 503.

No Vercel function is in the path and no model runs. Spec sections 9.6 and 9.8; owner steps and rollback: `ai-os/projexa-build-002/OWNER_SWITCH_ON_GUIDE.md`.

## Routes

| Route | Answer |
| --- | --- |
| `POST /run` `{"intent_id"}` | 200 `{intent_id, status: "done", submission_id, record: {id, route}}`; 200 `{status: "failed", code, missing}`; 200 `{status: "refused", code}` (`WRITES_NOT_ENABLED`, `ROLE_CHANGED`, `LINK_GONE`, `EXPIRED`, `NOT_CLAIMABLE`); 200 `{status: "executing"}` (another call runs it); 503 `CLAIM_UNAVAILABLE` (nothing was claimed) |
| `GET /health` | 200 `{ok: true, db_role}` (`app_runtime` when the connection string is the right one); 503 `DB_UNREACHABLE` |
| any route, secrets absent | 503 `{ok: false, code: "NOT_CONFIGURED", missing: [<setting names>]}` before anything is read |
| any route, wrong or no bearer | 401 `UNAUTHORIZED` |

## The two settings (owner-set; this repository never holds a value)

| Name | What it is | Where |
| --- | --- | --- |
| `AWL_EXEC_INTERNAL_SECRET` | A long random string. The `ai-work-link` function presents it as the bearer; this function compares it in constant time. Set on BOTH functions (Edge Function secrets are project-wide). | `supabase secrets set` |
| `APP_RUNTIME_DATABASE_URL` | The connection string of the `app_runtime` role through the pooler (the value Vercel's own setting of the same name holds). The business writes run through it under row-level security. | `supabase secrets set` |

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` are platform-injected; the service-role client calls `ai_work_link_intent_claim` and `ai_work_link_intent_finish` (granted to `service_role` only, drizzle/0629).

## Build and deploy (the PM; never Vercel)

1. `bun run scripts/build-ai-work-link-exec.ts` writes `app.bundle.mjs` and prints `BUNDLE_OK bytes=<n>` (limit 5,000,000). `node scripts/verify/awl-exec-closure.mjs` first proves that no `next/*`, `next-intl`, `resend`, `xlsx`, `pdf-parse`, `mathjs`, model client or spawned process is reachable.
2. Deploy the folder with `verify_jwt` false (the caller presents the shared secret, not a JWT).
3. The `ai-work-link` function is redeployed with `EXEC_FUNCTION_PRESENT = true` only AFTER the two settings above are set and the pre-flight (`scripts/verify/awl-exec-preflight.sh`) prints `AWL_EXEC_READY db_role=app_runtime`.

## What a run does

`ai_work_link_intent_claim` re-resolves the link and the person live and recomputes what the person may do NOW (a demoted person is refused `ROLE_CHANGED`); then `runDirectTask` runs with `via 'ai_link'` and the link id (text cleaned and capped at 2,000 characters, the project pinned, another project's ids refused, no model call, the task recorded as executor `ai` with `model_calls` 0, memory stored without an embedding); then `ai_work_link_intent_finish` stores `{id, route}` or a closed failure code. A crash between the write and the finish leaves the intent `executing`, which reads `failed EXECUTION_UNCERTAIN` after 10 minutes and is never run again.

The automation-rule trigger that a progress or labour write fires in the app is skipped here (`scripts/awl-exec-aliases.mjs` says why).

## Local execution host

`scripts/awl-local-exec-host.ts` serves this same handler on 127.0.0.1 over the same pipeline, so a persona run can prove real writes before anything is switched on. `--dry` uses an in-process PGlite database.
